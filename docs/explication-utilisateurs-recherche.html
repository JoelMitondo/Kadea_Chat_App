Trois fonctions pour trouver des gens et des messages, et pour s'en protéger :

  • la page Utilisateurs, pour chercher quelqu'un et lancer une discussion ;
  • la recherche dans ses propres messages ;
  • le blocage d'une personne.

Trois techniques à retenir dans ce lot :

• La pagination avec paginate() : on ne charge jamais tous les utilisateurs.

• La recherche en direct avec le « debounce » et un numéro de requête qui ignore les réponses arrivées en retard.

• Une recherche limitée à ses propres conversations, grâce à une jointure sur user_conversations.

1. Les routes et les validateurs

Toutes sont dans le groupe middleware.auth(). Les identifiants d'utilisateur sont des UUID (par exemple 3f2a9c1e-…), d'où le matcher ID_UUID.

// app/validators/user_list.ts
export const searchUsersValidator = vine.create({
  q: vine.string().trim().maxLength(100).optional(),
  page: vine.number().min(1).optional(),
})

export const chatWithUserValidator = vine.create({
  id: vine.string().uuid(),
})

// app/validators/search.ts
export const searchMessagesValidator = vine.create({
  q: vine.string().trim().maxLength(100).optional(),
})
  • q : le texte cherché, facultatif, 100 caractères au plus.
  • page : un nombre au moins égal à 1. VineJS convertit "2" (venu de l'adresse) en 2.
  • chatWithUserValidator vérifie qu'un identifiant est un vrai UUID. Il est utilisé ici et par les groupes (retrait d'un membre). Le commentaire rappelle qu'un identifiant invalide ferait sinon planter PostgreSQL.
  • Comment validateUsing lit-il ?q=marie ? Pour une requête GET, il n'y a pas de corps. request.validateUsing valide request.all(), qui rassemble le corps et la « query string » (ce qui suit le ?).

2. donnePageUtilisateurs : la liste paginée

const USERS_PER_PAGE = 20

async donnePageUtilisateurs({ auth, request, view }: HttpContext) {
  const currentUser = auth.getUserOrFail()
  const { q, page } = await request.validateUsing(searchUsersValidator)
  const search = q ?? ''

20 personnes par page. search vaut le texte cherché, ou une chaîne vide s'il n'y en a pas. C'est plus simple à manipuler qu'undefined.

  const query = User.query().whereNot('id', currentUser.id).orderBy('fullName', 'asc')

  if (search !== '') {
    query.whereILike('fullName', `%${protegeCaracteresRecherche(search)}%`)
  }
  • Tous les utilisateurs sauf moi, par ordre alphabétique.
  • On construit la requête par étapes : query n'est pas encore exécutée (pas d'await), et on y ajoute le filtre seulement s'il y a une recherche.
  • whereILike('fullName', '%marie%') : le nom contient « marie », quelle que soit la casse (Marie, MARIE…). Les % veulent dire « n'importe quoi avant et après ».
  • protegeCaracteresRecherche empêche qu'un % ou un _ tapé serve de joker (voir le fichier sur les services).
  const paginator = await query.paginate(page ?? 1, USERS_PER_PAGE)

paginate(numéroDePage, parPage) exécute deux requêtes :

  1. un COUNT pour connaître le nombre total de résultats, et donc le nombre de pages ;
  2. la page demandée, avec LIMIT 20 OFFSET 20 × (page − 1). Pour la page 3, la base saute 40 lignes et en prend 20.

Il renvoie un objet « paginateur » qui contient les lignes et des informations comme currentPage et lastPage. Même avec 10 000 inscrits, on ne charge que 20 personnes.

  const users = paginator.all().map((person) => ({
    id: person.id,
    fullName: person.fullName,
    initials: donneInitiales(person.fullName),
    avatarUrl: person.avatarUrl,
    email: person.email,
    isOnline: person.isOnline,
    createdAt: formateDate(person.createdAt),
  }))

paginator.all() donne les lignes de la page. On ne garde que ce que la vue affiche, en préparant les initiales et la date lisible.

  const buildUrl = (pageNumber: number) =>
    `/users?q=${encodeURIComponent(search)}&page=${pageNumber}`

  const data = {
    users,
    search,
    pagination: {
      currentPage: paginator.currentPage,
      lastPage: paginator.lastPage,
      previousUrl: paginator.currentPage > 1 ? buildUrl(paginator.currentPage - 1) : null,
      nextUrl: paginator.currentPage < paginator.lastPage ? buildUrl(paginator.currentPage + 1) : null,
    },
  }
  • buildUrl fabrique l'adresse d'une page en gardant la recherche en cours. Sinon, cliquer sur « Suivant » pendant une recherche « marie » afficherait la page 2 de tous les utilisateurs.
  • encodeURIComponent(search) protège les caractères spéciaux dans une adresse. « Jean & Marie » deviendrait sinon ?q=Jean & Marie, et le & serait pris pour le début d'un nouveau paramètre.
  • previousUrl / nextUrl valent null sur la première et la dernière page. La vue n'affiche alors pas le lien correspondant.
  if (request.header('x-requested-with') === 'XMLHttpRequest') {
    return view.render('partials/users-list', data)
  }
  return view.render('pages/users', data)
}

Le même principe que l'ouverture d'une conversation. Pour la recherche en direct (fetch avec X-Requested-With), on renvoie seulement la liste (partials/users-list), que le script place dans la page. Sinon (adresse tapée, rechargement, lien de pagination), on renvoie la page entière, qui inclut la même partial. Le HTML d'une ligne est donc écrit une seule fois.

3. ouvreDiscussion : le bouton « Discuter »

async ouvreDiscussion({ auth, params, response, session }: HttpContext) {
  const currentUser = auth.getUserOrFail()
  const { id } = await chatWithUserValidator.validate({ id: params.id })

  if (id === currentUser.id) {
    session.flash('error', 'Vous ne pouvez pas discuter avec vous-même.')
    return response.redirect().toRoute('users')
  }

  const otherUser = await User.findOrFail(id)
  const conversation = await chercheOuCreeConversationPrivee(currentUser, otherUser)

  return response.redirect().toRoute('conversations.show', { id: conversation.id })
}
  • chatWithUserValidator.validate({ id: params.id }) : on valide un objet fabriqué à la main, puisque l'identifiant vient de l'adresse et pas du corps de la requête.
  • Pas de discussion avec soi-même. Sa propre ligne n'apparaît pas dans la liste, mais une requête modifiée à la main pourrait le tenter.
  • User.findOrFail(id) : 404 si la personne n'existe pas (compte supprimé entre-temps).
  • chercheOuCreeConversationPrivee renvoie la conversation existante, ou la crée (voir le fichier sur les services, avec le double whereHas).
  • Une redirection vers /conversations/:id : la page Messages s'ouvre directement sur cette conversation. Si elle avait été supprimée de ma liste (removedAt), elle reste visible car c'est celle qu'on ouvre (voir le fichier sur les conversations).
  • Pourquoi un POST et pas un simple lien ? Parce que l'action peut créer une conversation en base, et une requête GET ne doit jamais rien modifier. Le POST est aussi protégé par le jeton CSRF.

5. users.js : recherche en direct et fenêtre « Voir plus »

document.body.dataset.loaderFetch = 'off'

loaderFetch = 'off' écrit data-loader-fetch="off" sur <body>. loader.js, qui affiche un chargeur pendant les requêtes, lit cet attribut et ne s'affiche pas. Avec une requête à chaque pause de frappe, le chargeur clignoterait sans arrêt.

La recherche, avec deux protections

let minuteur = null
let numeroRecherche = 0

async function rechercher() {
  let texte = champ.value.trim()

  numeroRecherche = numeroRecherche + 1
  let monNumero = numeroRecherche

  let reponse
  try {
    reponse = await fetch('/users?q=' + encodeURIComponent(texte), {
      headers: { 'X-Requested-With': 'XMLHttpRequest' },
    })
  } catch (erreurReseau) {
    kcNotifier.erreur('Impossible de contacter le serveur. Vérifiez votre connexion.')
    return
  }
  if (!reponse.ok) {
    kcNotifier.erreur('La recherche a échoué. Veuillez réessayer.')
    return
  }

  let html = await reponse.text()

  if (monNumero !== numeroRecherche) { return }

  resultats.innerHTML = html
  history.replaceState(null, '', texte === '' ? '/users' : '/users?q=' + encodeURIComponent(texte))
}
  • L'en-tête X-Requested-With dit au serveur « c'est le JavaScript ». Il renvoie alors seulement la liste.
  • reponse.text() : la réponse est du HTML, pas du JSON. On l'insère directement avec innerHTML. C'est sans risque, car ce HTML vient de notre serveur et Edge a déjà échappé les données.
  • Le numéro de recherche, contre les réponses en retard :
    1. Je tape « ma ». La recherche n°1 part.
    2. Je continue : « marie ». La recherche n°2 part.
    3. La n°2 (moins de résultats) répond avant la n°1.
    4. Sans le numéro, la n°1 arriverait ensuite et remplacerait les bons résultats par ceux de « ma ».
    Chaque recherche note son numéro dans monNumero. Quand la réponse arrive, si numeroRecherche a augmenté entre-temps, une recherche plus récente existe, et on jette la réponse.
  • history.replaceState met à jour l'adresse (/users?q=marie) sans recharger la page et sans ajouter d'entrée dans l'historique. On peut recharger ou partager la page avec la recherche, et le bouton « Retour » ne repasse pas par chaque lettre tapée. pushState, lui, aurait ajouté une entrée à chaque recherche.
champ.addEventListener('input', function () {
  clearTimeout(minuteur)
  minuteur = setTimeout(rechercher, 300)
})

formulaire.addEventListener('submit', function (evenement) {
  evenement.preventDefault()
  clearTimeout(minuteur)
  rechercher()
})
  • Le « debounce », décrit dans le commentaire du fichier : à chaque touche, on annule le minuteur et on en relance un de 300 ms. La recherche ne part que quand on s'arrête de taper. Pour « marie », cela fait 1 requête au lieu de 5.
  • La touche Entrée déclenche submit. On bloque le rechargement (preventDefault), on annule le minuteur en cours et on cherche tout de suite.

6. search_controller.ts : chercher dans ses messages

Le début

const RESULTS_LIMIT = 50

async donnePageRecherche({ auth, request, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const { q } = await request.validateUsing(searchMessagesValidator)
  const search = q ?? ''

  if (search.length < 2) {
    return view.render('pages/search', { search, results: [], hasSearched: false })
  }
  • Au plus 50 résultats, les plus récents.
  • Moins de 2 caractères : on affiche seulement le champ. Chercher « a » renverrait presque tous les messages, pour rien. hasSearched: false permet à la vue d'afficher une invitation à chercher, et non « aucun résultat ».

La requête

  const rows = await db
    .from('messages')
    .join('user_conversations as me', 'me.conversation_id', 'messages.conversation_id')
    .join('conversations', 'conversations.id', 'messages.conversation_id')
    .join('conversation_types', 'conversation_types.id', 'conversations.conversation_type_id')
    .join('users as sender', 'sender.id', 'messages.user_id')
    .where('me.user_id', user.id)
    .where('messages.is_deleted', false)
    .whereILike('messages.content', `%${protegeCaracteresRecherche(search)}%`)
    .where((query) => {
      query.whereNull('me.removed_at').orWhereRaw('messages.created_at > me.removed_at')
    })
    .orderBy('messages.created_at', 'desc')
    .limit(RESULTS_LIMIT)
    .select(
      'messages.id', 'messages.content', 'messages.created_at', 'messages.conversation_id',
      'conversations.title', 'conversation_types.type', 'sender.full_name as sender_name'
    )

C'est la requête la plus riche du projet, écrite avec db.from (le constructeur de requêtes SQL) plutôt qu'avec un modèle, car elle rassemble des colonnes de cinq tables.

LigneRôle
join('user_conversations as me', ...) + where('me.user_id', user.id)La sécurité : on ne garde que les messages des conversations dont je fais partie. as me donne un surnom à la table, pour lire « ma participation ».
join('conversations', ...)Pour le titre (nom du groupe)
join('conversation_types', ...)Pour savoir si c'est un groupe ou une conversation privée
join('users as sender', ...)Pour le nom de l'auteur du message (sender)
where('messages.is_deleted', false)Pas les messages supprimés
whereILike('messages.content', '%mot%')Le texte contient le mot, sans tenir compte de la casse
where((query) => ...)La règle de removedAt (voir plus bas)
orderBy(... 'desc').limit(50)Les 50 plus récents
select(...)Seulement les colonnes utiles. 'sender.full_name as sender_name' renomme la colonne pour qu'elle ne se confonde pas avec d'autres.
  • Pourquoi des noms complets (messages.content, me.user_id) ? Plusieurs tables ont une colonne id ou user_id. Écrire seulement user_id serait ambigu, et PostgreSQL refuserait la requête.
  • Les parenthèses de where((query) => { ... }) : la fonction regroupe deux conditions entre parenthèses en SQL : AND (me.removed_at IS NULL OR messages.created_at > me.removed_at). Sans ce regroupement, le OR s'appliquerait à toute la requête, et on trouverait des messages d'autres conversations.
  • La règle de removedAt, expliquée par le commentaire : si j'ai supprimé une conversation de ma liste, je ne cherche que dans les messages arrivés après. Les anciens sont cachés partout ailleurs, ils ne doivent pas réapparaître ici.
  • orWhereRaw('messages.created_at > me.removed_at') : on compare deux colonnes. where('a', '>', 'b') comparerait la colonne a au texte 'b', d'où le passage par du SQL brut. Il n'y a aucune valeur de l'utilisateur dedans, donc aucun risque d'injection.

Le nom des conversations privées

  const privateIds = rows
    .filter((row) => row.type !== GROUP_TYPE)
    .map((row) => row.conversation_id as number)

  const otherNames = new Map<number, string>()

  if (privateIds.length > 0) {
    const others = await UserConversation.query()
      .whereIn('conversationId', privateIds)
      .whereNot('userId', user.id)
      .preload('user')

    for (const other of others) {
      otherNames.set(other.conversationId, other.user.fullName)
    }

  • Le problème : une conversation privée n'a pas de titre. Son nom affiché est celui de l'autre personne.
  • On rassemble les identifiants des conversations privées trouvées, puis on charge en une seule requête l'autre participant de chacune (whereNot('userId', user.id)).
  • Une Map de la forme 12 → 'Jo Kabila' permet ensuite de retrouver chaque nom instantanément.
  • Pourquoi pas une requête par résultat ? Avec 50 résultats, ce serait 50 requêtes. C'est le problème « N+1 », évité ici.
  • if (privateIds.length > 0) évite une requête inutile quand tous les résultats viennent de groupes.

La préparation des résultats

  const results = rows.map((row) => {

  • url : un clic sur le résultat ouvre le groupe ou la conversation qui contient le message.
  • as string / as number : db.from renvoie des lignes sans type précis, et on indique le type à TypeScript.

7. decoupeAutourDuMot : surligner le mot trouvé

private decoupeAutourDuMot(content: string, search: string) {
  const index = content.toLowerCase().indexOf(search.toLowerCase())

  if (index === -1) {
    return { before: content.slice(0, 120), match: '', after: '' }
  }

  const start = Math.max(0, index - 40)
  const end = Math.min(content.length, index + search.length + 80)

  return {
    before: (start > 0 ? '…' : '') + content.slice(start, index),
    match: content.slice(index, index + search.length),
    after: content.slice(index + search.length, end) + (end < content.length ? '…' : ''),
  }
}

Prenons le message « Bonjour à tous, n'oubliez pas la réunion de demain à 10 h dans la salle B », avec la recherche « RÉUNION ».

  1. Trouver le mot sans tenir compte de la casse : on met tout en minuscules des deux côtés, et indexOf donne la position du mot (ou -1).
  2. Un extrait autour du mot : au plus 40 caractères avant et 80 après. Math.max(0, …) et Math.min(longueur, …) empêchent de sortir du texte.
  3. Trois morceaux : before (« Bonjour à tous, n'oubliez pas la »), match (« réunion », écrit comme dans le message, pas comme dans la recherche, grâce à slice sur le texte d'origine) et after (« de demain à 10 h… »).
  4. Des points de suspension « … » sont ajoutés seulement si le texte a été coupé de ce côté.

La vue assemble : {{ result.before }}<mark>{{ result.match }}</mark>{{ result.after }}. <mark> est la balise HTML du surlignage.

Pourquoi découper côté serveur au lieu d'insérer <mark> dans le texte ? Pour pouvoir garder {{ }}, qui échappe le HTML, sur les trois morceaux. Si on fabriquait la chaîne "…<mark>réunion</mark>…" en JavaScript, il faudrait l'afficher avec {{{ }}} (sans échappement). Un message contenant <script> serait alors interprété. Avec les trois morceaux, seul le <mark> écrit dans la vue est du vrai HTML.

Le cas index === -1 (« ne devrait pas arriver », dit le commentaire) peut se produire avec certains caractères spéciaux. La base et JavaScript n'ont pas toujours exactement les mêmes règles de minuscules. On affiche alors simplement le début du message.

8. blocks_controller.ts : bloquer et débloquer

async bloque({ auth, params, request, response, session }: HttpContext) {
  const me = auth.getUserOrFail()
  const { id } = await chatWithUserValidator.validate({ id: params.id })

  if (id === me.id) {
    return response.unprocessableEntity({ message: 'Vous ne pouvez pas vous bloquer vous-même.' })
  }

  await User.findOrFail(id)
  await bloqueUtilisateur(me.id, id)

  if (request.accepts(['html', 'json']) === 'json') {
    return response.ok({ message: 'Utilisateur bloqué.' })
  }
  session.flash('success', 'Utilisateur bloqué.')
  return response.redirect().back()
}
  • On ne se bloque pas soi-même (422).
  • User.findOrFail(id) : 404 si la personne n'existe pas. On évite de créer un blocage vers un compte inexistant.
  • bloqueUtilisateur utilise firstOrCreate : bloquer deux fois ne crée pas de doublon (voir le fichier sur les services).
  • Deux façons de répondre :
    • en JSON pour le bouton de la discussion, qui passe par fetch dans message.js ;
    • en redirection avec message flash pour un formulaire classique. redirect().back() renvoie sur la page d'où vient la requête.
async debloque({ auth, params, request, response, session }: HttpContext) {
  const me = auth.getUserOrFail()
  const { id } = await chatWithUserValidator.validate({ id: params.id })

  await debloqueUtilisateur(me.id, id)
  ... même réponse JSON ou redirection ...
}

Débloquer supprime la ligne. Pas besoin de vérifier que la personne existe : supprimer un blocage qui n'existe pas ne fait simplement rien.

Où sont les boutons ?

  • Dans une conversation privée (chat-panel.edge) : un bouton « Bloquer » (data-block-user), ou « Débloquer » si chat.blockedByMe. message.js les gère avec changerBlocage : confirmation, POST vers /users/:id/block ou /unblock, notification, puis rechargement du panneau pour afficher le bandeau orange et le bon bouton.
  • Dans les paramètres : la liste des personnes bloquées, avec un formulaire classique « Débloquer » chacune (lot 4).

10. Ce qui a été remarqué

Ce qui est bien fait, à mettre en avant :

• La pagination, et des adresses de page qui gardent la recherche en cours.

• La recherche en direct avec debounce, protection contre les réponses en retard, et adresse mise à jour sans encombrer l'historique.

• Un seul fichier pour une ligne d'utilisateur, qu'elle soit affichée au chargement ou après une recherche.

• La recherche de messages limitée à ses conversations, qui respecte removedAt et les messages supprimés, sans problème N+1.

• Le surlignage sans jamais désactiver l'échappement, et textContent dans la fenêtre « Voir plus ».

1. L'adresse e-mail de chaque inscrit est visible par tous. La liste écrit data-email="{{ person.email }}" pour chaque personne, et n'importe quel utilisateur connecté peut parcourir toutes les pages pour récupérer toutes les adresses. C'est un choix fonctionnel, mais discutable pour la vie privée (et au regard des lois sur les données personnelles). On pourrait ne plus afficher l'e-mail, ou seulement aux personnes avec qui on a déjà une conversation.

2. La recherche dans les messages ne passera pas bien à l'échelle. ILIKE '%mot%' commence par un % : aucun index classique ne peut servir, et PostgreSQL lit tous les messages des conversations concernées. Avec beaucoup de messages, un index « trigramme » (extension pg_trgm, index GIN sur messages.content) rendrait la recherche rapide.

3. page accepte un nombre à virgule. vine.number().min(1) laisse passer ?page=1.5, ce qui donne un décalage bizarre (la page commence au 11ᵉ utilisateur). Il suffit d'ajouter .withoutDecimals(), comme dans olderMessagesValidator.

4. Le blocage est à sens unique. Celui qui bloque peut toujours écrire à la personne bloquée, qui ne peut pas lui répondre. Si c'est voulu, il faudrait l'expliquer dans la confirmation (« Il ne pourra plus vous envoyer de nouveaux messages » le dit à moitié). Sinon, la règle ecrireA pourrait aussi vérifier aBloque(user.id, otherUserId).

5. Dans users.js, le message d'erreur ne tient pas compte du numéro de recherche. Si une ancienne recherche échoue alors qu'une plus récente a réussi, une notification d'erreur s'affiche pour rien. Il suffit de déplacer le test monNumero !== numeroRecherche avant les messages d'erreur.
