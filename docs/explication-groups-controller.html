groups_controller.ts expliqué ligne par ligne

Kadea Chat · les groupes : liste, ouverture, historique, recherche de membres, création, ajout, retrait, suppression · fichier : app/controllers/groups_controller.ts

Ce contrôleur gère tout ce qui concerne les groupes, sauf l'envoi de messages (c'est messages_controller.ts qui s'en charge, avec enregistreMessageGroupe).

Un groupe, c'est quoi en base ? Une ligne de conversations dont le type est 'Publique', avec un titre (le nom du groupe). Chaque membre a une ligne dans user_conversations, et cette ligne porte son rôle : 'admin' ou 'membre'.

La sécurité se fait en deux étages :

• Es-tu membre ? chercheParticipationGroupe répond. Sinon, 404 : on ne dit même pas que le groupe existe.

• As-tu le droit ? La policy GroupPolicy (Bouncer) répond pour les actions réservées à l'admin : ajouter, retirer, supprimer. Sinon, 403. Le rôle est toujours relu en base, jamais déduit de ce que la page affiche.

Même principe que les conversations privées : ouvrir un groupe depuis le JavaScript renvoie seulement le panneau, ouvrir l'adresse directement renvoie la page entière. L'historique est paginé par 50 messages.

Mis à jour le 06/11/2026 pour suivre les corrections P0, P1 et P2 : policies Bouncer, retrait d'un membre, recherche de candidats limitée côté serveur, messages précédents, outils partagés de chat_service.ts et alias #services/....

2. La policy Bouncer : app/policies/group_policy.ts

Bouncer est le système d'autorisation d'AdonisJS. Une policy rassemble les règles « qui a le droit de faire quoi » sur une ressource. Avant, chaque action avait son propre if (membership.role.title !== ADMIN_ROLE). Maintenant, les règles sont écrites une seule fois, avec un nom.

function estAdministrateur(membership: UserConversation) {
  return membership.role.title === ADMIN_ROLE
}

export default class GroupPolicy extends BasePolicy {
  ajouterMembres(_user: User, membership: UserConversation) {
    if (!estAdministrateur(membership)) {
      return AuthorizationResponse.deny("Seul l'administrateur du groupe peut ajouter des membres.")
    }
    return true
  }

  retirerMembres(_user: User, membership: UserConversation) { /* même chose, message « retirer » */ }

  // La personne visée par un retrait : un administrateur ne peut pas être retiré
  retirerCeMembre(_user: User, target: UserConversation) {
    if (estAdministrateur(target)) {
      return AuthorizationResponse.deny('Un administrateur ne peut pas être retiré.')
    }
    return true
  }

  supprimer(_user: User, membership: UserConversation) { /* même chose, message « supprimer » */ }
}
  • Le premier paramètre est toujours l'utilisateur connecté, que Bouncer fournit tout seul. Ici, il n'est pas utilisé : le rôle est déjà dans membership. Le _ devant _user est une convention pour dire « paramètre volontairement ignoré ».
  • membership est la participation de l'utilisateur au groupe, avec son rôle chargé (.preload('role')). Sans ce preload, membership.role serait vide.
  • return true veut dire autorisé. AuthorizationResponse.deny('...') veut dire refusé, avec un message en français.
  • retirerCeMembre regarde la personne visée (target), et non celui qui agit : on ne peut pas retirer un administrateur.

Côté contrôleur, une seule ligne :

await bouncer.with(GroupPolicy).authorize('ajouterMembres', membership)

Si la règle refuse, authorize lance une erreur E_AUTHORIZATION_FAILURE. La suite de la méthode n'est pas exécutée. app/exceptions/handler.ts transforme cette erreur en réponse 403, avec le message français de la policy. bouncer est disponible dans le contexte grâce au middleware initialize_bouncer_middleware.ts.

3. donnePageGroupes : la page sans groupe ouvert

async donnePageGroupes({ auth, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const groups = await this.donneListeGroupes(user)
  const candidates = await this.donneCandidats([user.id]) // pour la popup de création

  return view.render('pages/groups', { groups, chat: null, candidates })
}
  • auth.getUserOrFail() : l'utilisateur connecté. Le middleware auth de la route garantit qu'il existe.
  • donneListeGroupes(user) : la colonne de gauche, avec les groupes de l'utilisateur (voir plus bas).
  • donneCandidats([user.id]) : la première liste de personnes affichée dans la fenêtre « Créer un groupe », au plus 20, par ordre alphabétique. On s'exclut soi-même. Quand on tape un nom, groupe.js interroge donneCandidatsRecherche pour chercher dans tous les inscrits.
  • chat: null : aucun groupe ouvert. La vue affiche alors le message d'accueil à droite.

4. donneGroupe : ouvrir un groupe

async donneGroupe({ auth, params, request, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const chat = await this.donneDiscussion(user, Number(params.id))
  • params.id : la partie :id de l'adresse /groups/12. Le matcher de la route l'a déjà converti en nombre. Number(...) reste comme sécurité.
  • donneDiscussion : prépare tout ce qu'il faut pour afficher le groupe (infos, membres, première page de messages) et vérifie que l'utilisateur est membre. Sinon, 404.
  if (request.header('x-requested-with') === 'XMLHttpRequest') {
    return view.render('partials/group-panel', { chat })
  }

  const groups = await this.donneListeGroupes(user)
  const candidates = await this.donneCandidats([user.id])
  return view.render('pages/groups', { groups, chat, candidates })
}
  • Si la demande vient du JavaScript (en-tête X-Requested-With: XMLHttpRequest), on renvoie seulement le panneau de droite. Le script le place dans la page sans la recharger.
  • Sinon (adresse tapée, nouvel onglet, rechargement), on renvoie la page complète : la liste, la fenêtre de création et le groupe ouvert.
  • donneDiscussion est appelée avant le test. Le panneau seul n'a pas besoin de la liste ni des candidats, ce qui évite deux requêtes pour la version JavaScript, la plus fréquente.

5. donneMessagesPrecedents : l'historique plus ancien

async donneMessagesPrecedents({ auth, params, request, response, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const conversationId = Number(params.id)
  const { before } = await olderMessagesValidator.validate(request.qs())

  // Seuls les membres du groupe peuvent lire ses messages (sinon : erreur 404)
  await chercheParticipationGroupe(user.id, conversationId).firstOrFail()

  const page = await this.chargeMessages(conversationId, user.id, before)

  return response.ok({
    html: await view.render('partials/messages-page', {
      messages: page.messages.map((message) => construitVueMessage(message, user.id, true)),
    }),
    hasMore: page.hasMore,
    oldestId: page.oldestId,
    dropFirstSeparator: await memeJourQueLePremierAffiche(page.messages, conversationId, before),
  })
}

C'est la version groupe de la méthode du même nom dans conversations_controller.ts. Le fichier sur les conversations l'explique en détail, ainsi que le JavaScript qui l'appelle.

  • request.qs() : ce qui suit le ?, par exemple { before: '345' }. olderMessagesValidator.validate(...) vérifie que c'est un entier positif et le convertit en nombre.
  • Le contrôle d'accès : on ne garde pas le résultat de firstOrFail(). On veut seulement la 404 si tu n'es pas membre. Sans ce contrôle, n'importe qui pourrait lire l'historique d'un groupe en devinant son numéro.
  • chargeMessages(..., before) : les 50 messages qui précèdent le message before. Voir le point 14.
  • construitVueMessage(message, user.id, true) : le true affiche le nom de l'auteur au-dessus des bulles des autres, comme partout dans un groupe.
  • La réponse JSON :
    • html : les bulles déjà prêtes, avec le même composant message-list qu'à l'ouverture ;
    • hasMore : reste-t-il des messages plus anciens ?
    • oldestId : le prochain curseur ;
    • dropFirstSeparator : faut-il retirer un séparateur de jour qui apparaîtrait sinon deux fois ?

Dans app/services/group.ts :

export async function creeGroupe(creator: User, name: string, memberIds: string[]): Promise<Conversation> {
  const groupType = await donneTypeConversation(GROUP_TYPE)
  const adminRole = await donneRole(ADMIN_ROLE)
  const memberRole = await donneRole(MEMBER_ROLE)

  return db.transaction(async (trx) => {
    const conversation = await Conversation.create(
      { conversationTypeId: groupType.id, createdById: creator.id, title: name },
      { client: trx }
    )

    await UserConversation.createMany(
      [
        { conversationId: conversation.id, userId: creator.id, roleId: adminRole.id },
        ...memberIds.map((userId) => ({ conversationId: conversation.id, userId, roleId: memberRole.id })),
      ],
      { client: trx }
    )
    return conversation
  })
}
  • donneTypeConversation et donneRole viennent de chat_service.ts. Ce sont de simples firstOrCreate : 
    export function donneRole(title: string) {
  return RoleConversation.firstOrCreate({ title }, { title })
}
    Ils cherchent la ligne et la créent si elle manque. Même sur une base toute neuve, sans seeder, le type « Publique » et les rôles existent. On récupère leur id.
  • db.transaction : tout ce qui est fait avec trx est enregistré ensemble ou pas du tout. Pas de groupe vide si l'ajout des membres échoue. { client: trx } rattache chaque requête à la transaction.
  • createMany : crée plusieurs lignes en une fois. Le créateur est ajouté avec le rôle admin, puis ...memberIds.map(...) étale une ligne « membre » par personne.
  await previensConversationAjoutee({ conversation: group, userIds: otherIds, lastMessage: null })

  session.flash('success', `Le groupe « ${name} » a été créé.`)
  return response.created({ id: group.id })
}
  • Temps réel : chaque membre (sauf le créateur) reçoit conversation:added, avec la ligne HTML du groupe pour sa liste et l'aperçu « Aucun message ».
  • session.flash : un message gardé pour la prochaine page affichée seulement.
  • response.created : code 201, avec l'identifiant du groupe. groupe.js fait alors window.location.href = '/groups/' + id, et c'est cette page qui affiche le message flash.

export function chercheParticipationGroupe(userId: User['id'], conversationId: number) {
  return chercheParticipation(userId, conversationId, GROUP_TYPE)
}

function chercheParticipation(userId: User['id'], conversationId: number, typeName: string) {
  return UserConversation.query()
    .where('userId', userId)
    .where('conversationId', conversationId)
    .whereHas('conversation', (conversationQuery) => {
      conversationQuery.whereHas('type', (typeQuery) => {
        typeQuery.where('type', typeName)
      })
    })
}
  • Une requête commune pour le privé et les groupes : chercheParticipationPrivee appelle la même fonction avec PRIVATE_TYPE. Avant, la requête était écrite deux fois.
  • Elle cherche ta participation à cette conversation, à condition que ce soit un groupe. whereHas veut dire « dont la relation vérifie cette condition ». Une conversation privée est refusée, même avec son numéro dans l'adresse /groups/:id.
  • Elle n'exécute pas la requête (pas de await, pas de first) : elle renvoie une requête en construction. Le contrôleur ajoute .preload('role'), indispensable pour la policy, et .preload('conversation'), pour le nom du groupe. Puis .firstOrFail() l'exécute, avec une 404 si aucune ligne n'est trouvée.
  • La policy vérifie ensuite que tu es admin. Sinon, 403 avec « Seul l'administrateur du groupe peut ajouter des membres. ».

Dans app/services/group.ts :

export async function ajouteMembresAuGroupe(conversationId: number, userIds: string[]): Promise<string[]> {
  const existingRows = await UserConversation.query()
    .where('conversationId', conversationId)
    .whereIn('userId', userIds)
    .select('user_id')

  const existingIds = existingRows.map((row) => row.userId)
  const newIds = userIds.filter((userId) => !existingIds.includes(userId))
  if (newIds.length === 0) {
    return []
  }

  const memberRole = await donneRole(MEMBER_ROLE)
  // Les nouveaux membres voient l'historique : leur "dernier message" est celui du groupe
  const lastMessage = await donneDernierMessage(conversationId)

  await UserConversation.createMany(
    newIds.map((userId) => ({ conversationId, userId, roleId: memberRole.id, lastMessageId: lastMessage?.id ?? null }))
  )
  return newIds
}
  • D'abord, qui est déjà membre ? On ne garde dans newIds que les autres. select('user_id') utilise le nom de la colonne en base, mais on lit row.userId : Lucid convertit entre les deux.
  • donneDernierMessage (de chat_service.ts) renvoie le message le plus récent du groupe, trié par id décroissant. Il sert à remplir lastMessageId du nouveau membre. Sans lui, le groupe apparaîtrait dans sa liste avec « Aucun message » alors qu'il en contient.
  • lastMessage?.id ?? null : l'identifiant, ou null si le groupe n'a pas de message.
  • La fonction renvoie la liste des personnes réellement ajoutées, et le contrôleur s'en sert pour savoir qui prévenir. Si toutes étaient déjà membres, rien n'est fait et la réponse est une 422.

Étape 4 : prévenir tout le monde en temps réel

  const lastMessage = await donneDernierMessage(conversationId, { withAuthor: true })

  await previensConversationAjoutee({ conversation: membership.conversation, userIds: addedIds, lastMessage })

Pour les nouveaux membres : on relit le dernier message, cette fois avec son auteur (withAuthor: true fait un preload('user')). L'aperçu d'un groupe s'écrit « Jo : le projet est rendu ». Chacun reçoit conversation:added, et le groupe apparaît dans sa liste.

  const allMembers = await UserConversation.query().where('conversationId', conversationId).select('user_id')
  const existingMemberIds = allMembers
    .map((row) => row.userId)
    .filter((id) => id !== user.id && !addedIds.includes(id))
  previensGroupeModifie(conversationId, existingMemberIds)

Pour les anciens membres : tous les membres, moins l'admin (il recharge sa page lui-même) et moins les nouveaux (déjà prévenus). Chacun reçoit group:updated. Si le groupe est ouvert chez lui, le panneau se recharge : la liste des membres et le compteur se mettent à jour. Pas de await : la fonction n'est pas asynchrone.

Étape 5 : la réponse

Elle est nouvelle. L'admin peut maintenant retirer quelqu'un du groupe. La personne retirée ne peut plus ni lire ni écrire dans le groupe.

export async function supprimeConversationEtFichiers(conversationId: number): Promise<string[]> {
  // 1. Les participants (pour les prévenir ensuite)
  const members = await UserConversation.query().where('conversationId', conversationId).select('user_id')
  const memberIds = members.map((member) => member.userId)

  // 2. Les liens des fichiers joints (à supprimer de Cloudinary après)
  const attachments = await MessageAttachment.query()
    .whereIn('messageId', Message.query().select('id').where('conversationId', conversationId))
    .select('file_path')
  const fileUrls = attachments.map((attachment) => attachment.filePath)

  // 3. La conversation est supprimée de la base (messages et participants avec elle)
  await Conversation.query().where('id', conversationId).delete()

  // 4. Les fichiers sont supprimés de Cloudinary
  await supprimeFichiers(fileUrls)

  return memberIds
}

Dans l'ordre inverse, si la base refusait, le groupe existerait encore… avec des images cassées. Dans cet ordre, le pire cas est un fichier oublié sur Cloudinary : de l'espace perdu, mais rien de cassé pour l'utilisateur.

private async donneCandidats(excludedIds: User['id'][], search?: string) {
  const query = User.query()
    .whereNotIn('id', excludedIds)
    .orderBy('fullName', 'asc')
    .limit(CANDIDATES_LIMIT)
  if (search) {
    query.whereILike('fullName', `%${protegeCaracteresRecherche(search)}%`)
  }
  const users = await query

  return users.map((person) => ({
    id: person.id,
    fullName: person.fullName,
    initials: donneInitiales(person.fullName),
    avatarUrl: person.avatarUrl,
    isOnline: person.isOnline,
  }))
}

  return search.replace(/[\\%_]/g, (character) => `\\${character}`)
}
    Dans un LIKE, % et _ sont des jokers. Si quelqu'un tapait %, la recherche trouverait tout le monde. La fonction met un \ devant ces caractères (et devant \ lui-même) pour qu'ils soient cherchés tels quels.

Ce qui a été remarqué

Corrigé depuis la première version de ce document :

• Identifiants non numériques : les routes portent .where('id', ID_NUMERIQUE) et .where('userId', ID_UUID). /groups/abc donne une 404, et plus une erreur 500.

• La liste des candidats ne charge plus tous les utilisateurs : au plus 20, avec une recherche faite par le serveur.

• On peut retirer un membre, avec toutes les protections : admin seulement, pas soi-même, pas un autre admin.

• L'historique est paginé : au-delà de 100 messages, rien n'était accessible avant.

• Les règles « réservé à l'admin » sont écrites une seule fois, dans la policy.

1. Double ajout simultané. ajouteMembresAuGroupe vérifie d'abord qui est déjà membre, puis insère. Deux demandes presque simultanées peuvent essayer d'insérer la même personne. La migration déclare table.unique(['user_id', 'conversation_id']), donc la base refuse le doublon et les données restent propres. Mais la seconde demande finit en erreur 500 au lieu d'un message clair.

2. Un membre ne peut toujours pas quitter un groupe de lui-même. Seul l'admin peut le retirer. Il n'y a pas non plus de « changer d'administrateur ». Si l'admin veut partir, il doit supprimer le groupe, ou supprimer son compte, ce qui transmet le rôle au membre le plus ancien.

3. Le membre retiré garde l'onglet ouvert ? Il reçoit conversation:removed et le panneau se ferme. S'il était déconnecté à ce moment-là, l'événement est perdu, mais sa prochaine requête vers le groupe obtiendra de toute façon une 404 : la sécurité ne dépend pas du temps réel.
