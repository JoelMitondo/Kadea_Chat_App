groups_controller.ts expliqué ligne par ligne

Kadea Chat · les groupes : liste, ouverture, création, ajout de membres, suppression · fichier : app/controllers/groups_controller.ts

Ce contrôleur gère tout ce qui concerne les groupes, sauf l'envoi de messages (c'est messages_controller.ts qui s'en charge, avec enregistreMessageGroupe).

Un groupe, c'est quoi en base ? Une ligne de conversations dont le type est 'Publique', avec un titre (le nom du groupe). Chaque membre a une ligne dans user_conversations, et cette ligne porte son rôle : 'admin' ou 'membre'.

La règle de sécurité du fichier : avant toute action sensible (ajouter des membres, supprimer le groupe), on relit le rôle de l'utilisateur dans la base. On ne fait jamais confiance au fait que le bouton n'était affiché qu'à l'admin.

Même principe que les conversations privées : ouvrir un groupe depuis le JavaScript renvoie seulement le panneau ; ouvrir l'adresse directement renvoie la page entière.

2. donnePageGroupes : la page sans groupe ouvert (lignes 36 à 42)

async donnePageGroupes({ auth, view }: HttpContext) {
  const user = auth.getUserOrFail()

La création elle-même, dans app/service/group.ts :

export async function creeGroupe(creator: User, name: string, memberIds: string[]): Promise<Conversation> {
  const groupType = await ConversationType.firstOrCreate({ type: GROUP_TYPE }, { type: GROUP_TYPE })
  const adminRole = await RoleConversation.firstOrCreate({ title: ADMIN_ROLE }, { title: ADMIN_ROLE })
  const memberRole = await RoleConversation.firstOrCreate({ title: MEMBER_ROLE }, { title: MEMBER_ROLE })
  • firstOrCreate(recherche, valeurs) : cherche une ligne qui correspond à recherche. Si elle existe, il la renvoie. Sinon, il la crée avec valeurs. Ainsi, même sur une base toute neuve (sans données de départ), le type « Publique » et les rôles « admin » et « membre » existent.
  • On récupère ces trois lignes pour connaître leur identifiant (groupType.id, adminRole.id...), qui sera écrit dans les autres tables.
  return db.transaction(async (trx) => {
    const conversation = await Conversation.create(
      { conversationTypeId: groupType.id, createdById: creator.id, title: name },
      { client: trx }
    )
  • db.transaction : tout ce qui est fait avec trx est enregistré ensemble ou pas du tout. Si l'ajout des membres échoue, la conversation créée juste avant est annulée : pas de groupe vide, sans membres.
  • { client: trx } : indique que cette requête fait partie de la transaction. Sans lui, elle serait enregistrée tout de suite, en dehors.
  • La conversation reçoit le type groupe, son créateur et son titre (le nom du groupe).
    await UserConversation.createMany(
      [
        { conversationId: conversation.id, userId: creator.id, roleId: adminRole.id },
        ...memberIds.map((userId) => ({ conversationId: conversation.id, userId, roleId: memberRole.id })),
      ],
      { client: trx }
    )
    return conversation
  })
}
  • createMany : crée plusieurs lignes en une fois.
  • La première ligne : le créateur, avec le rôle admin.
  • ...memberIds.map(...) : transforme chaque identifiant en une ligne « membre », puis les ... étalent ces lignes dans le tableau, à la suite de celle du créateur.
  • La fonction renvoie la conversation créée : le contrôleur a besoin de son identifiant.

Temps réel : pour chaque membre (sauf le créateur), le serveur fabrique la ligne HTML du groupe pour la liste de gauche, puis l'envoie avec un événement conversation:added. lastMessage: null car un groupe neuf n'a aucun message : l'aperçu affichera « Aucun message ». Les membres qui ont la page Groupes ouverte voient le groupe apparaître sans recharger.

  session.flash('success', `Le groupe « ${name} » a été créé.`)

}
  • session.flash : un message gardé en session pour la prochaine page affichée seulement.
  • response.created : code 201 (« créé »), avec l'identifiant du groupe en JSON.

Étape 1 : est-il membre, et administrateur ?

chercheParticipationGroupe vient de chat_service.ts :

export function chercheParticipationGroupe(userId: User['id'], conversationId: number) {
  return UserConversation.query()
    .where('userId', userId)
    .where('conversationId', conversationId)
    .whereHas('conversation', (conversationQuery) => {
      conversationQuery.whereHas('type', (typeQuery) => {
        typeQuery.where('type', GROUP_TYPE)
      })
    })
}
  • Elle cherche la participation de cet utilisateur à cette conversation…
  • … à condition que la conversation soit un groupe. whereHas veut dire « dont la relation vérifie cette condition ». Ici, deux niveaux : la conversation, puis son type. Une conversation privée est donc refusée, même si on met son identifiant dans l'adresse /groups/:id.
  • Elle n'exécute pas la requête (pas de await, pas de first). Elle renvoie une requête en construction, que chaque appelant complète. C'est pour cela que le contrôleur peut enchaîner .preload(...) puis .firstOrFail().

De retour dans le contrôleur :

  • .preload('role') : charge le rôle de l'utilisateur dans ce groupe (admin ou membre).
  • .preload('conversation') : charge le groupe lui-même. Il servira pour la notification temps réel (nom et identifiant).
  • .firstOrFail() : exécute la requête et prend la première ligne. S'il n'y en a aucune (pas membre, pas un groupe, groupe inexistant), AdonisJS répond 404. On ne dit pas à un inconnu que le groupe existe.
  if (membership.role.title !== ADMIN_ROLE) {
    return response.forbidden({
      message: "Seul l'administrateur du groupe peut ajouter des membres.",
    })
  }

Il est membre, mais pas admin : code 403 (« interdit »). La différence avec 404 : ici, l'utilisateur fait partie du groupe, il sait déjà qu'il existe. On lui explique simplement qu'il n'a pas le droit.

Dans app/service/deletion_service.ts :

export async function supprimeConversationEtFichiers(conversationId: number): Promise<string[]> {
  // 1. Les participants (pour les prévenir ensuite)
  const members = await UserConversation.query().where('conversationId', conversationId).select('user_id')
  const memberIds = members.map((member) => member.userId)

  // 2. Les liens des fichiers joints (à supprimer de Cloudinary après)
  const attachments = await MessageAttachment.query()
    .whereIn('messageId', Message.query().select('id').where('conversationId', conversationId))
    .select('file_path')
  const fileUrls = attachments.map((attachment) => attachment.filePath)

  // 3. La conversation est supprimée de la base (messages et participants avec elle)
  await Conversation.query().where('id', conversationId).delete()

  // 4. Les fichiers sont supprimés de Cloudinary
  await supprimeFichiers(fileUrls)

  return memberIds
}
  1. Les participants d'abord : une fois le groupe supprimé, impossible de savoir qui en faisait partie. On les note pour les prévenir.
  2. Les liens des fichiers : une sous-requête. Message.query().select('id')... n'est pas exécutée seule : elle est placée dans le whereIn. En SQL : WHERE message_id IN (SELECT id FROM messages WHERE conversation_id = 12). Tout se fait en une seule requête.
  3. La suppression en cascade : on ne supprime que la ligne de conversations. Dans les migrations, les clés étrangères sont déclarées avec .onDelete('CASCADE') : PostgreSQL supprime alors automatiquement les messages de la conversation, puis leurs pièces jointes et leurs statuts, ainsi que les participations.
  4. Cloudinary en dernier : supprimeFichiers appelle supprimeFichierParLien pour chaque lien. Un échec est noté dans les logs sans tout bloquer.

Pourquoi la base d'abord, Cloudinary ensuite ? Le commentaire du fichier l'explique : une suppression en base peut être refusée, mais un fichier effacé de Cloudinary ne revient jamais. Dans l'ordre inverse, si la base refusait, le groupe existerait encore… avec des images cassées. Dans cet ordre, le pire cas est un fichier resté sur Cloudinary sans être utilisé : de l'espace perdu, mais rien de cassé pour l'utilisateur.

  previensConversationSupprimee({
    userIds: memberIds.filter((memberId) => memberId !== user.id),
    conversationId,
    kind: 'group',
    message: `Le groupe « ${groupName} » a été supprimé par son administrateur.`,

  • Les vérifications du navigateur servent au confort : elles évitent un aller-retour inutile. La sécurité, elle, est assurée par le serveur, qui revérifie tout. N'importe qui peut envoyer une requête sans passer par la page.

Le parcours complet : Ana crée « Projet Kadea » avec Jo et Mia

  1. Ana remplit la fenêtre et clique « Créer ». groupe.js vérifie le nom et le nombre de membres, puis envoie POST /groups avec { name, member_ids: [Jo, Mia] }.
  2. enregistreGroupe valide, retire Ana de la liste si besoin, et vérifie que Jo et Mia existent.
  3. creeGroupe crée, dans une seule transaction, la conversation « Publique » et trois participations : Ana (admin), Jo et Mia (membres).
  4. previensConversationAjoutee envoie à Jo et Mia la ligne HTML du groupe. Le groupe apparaît dans leur liste, avec « Aucun message ».
  5. Ana reçoit 201 { id: 42 }, son navigateur ouvre /groups/42, et le toast « Le groupe a été créé » s'affiche.
  6. Plus tard, Ana ajoute Léo : ajouteMembres vérifie qu'elle est admin et ajoute Léo avec le bon lastMessageId. Léo reçoit conversation:added ; Jo et Mia reçoivent group:updated et leur panneau se recharge.
  7. Ana supprime le groupe : la base supprime tout en cascade, puis Cloudinary efface les fichiers. Jo, Mia et Léo reçoivent conversation:removed et le groupe disparaît de leur écran.

Ce qui a été remarqué

Ce ne sont pas des erreurs bloquantes. Ce sont des points à connaître, éventuellement à améliorer plus tard.

1. Number(params.id) sans vérification. Avec /groups/abc, Number('abc') donne NaN. La requête SQL échoue alors, et l'utilisateur obtient probablement une erreur 500 au lieu d'une 404. C'est le même cas que dans les autres contrôleurs. Une solution : limiter la route aux nombres avec .where('id', router.matchers.number()).

2. donneCandidats charge tous les utilisateurs. C'est le cas à chaque ouverture de la page Groupes, et à chaque rechargement complet d'un groupe (la fenêtre de création est dans la page). Avec quelques dizaines de comptes, ce n'est pas un problème. Avec des milliers, la page deviendrait lourde. Une recherche à la demande, comme dans users.js, passerait mieux à l'échelle.

3. Deux ajouts simultanés. ajouteMembresAuGroupe vérifie d'abord qui est déjà membre, puis insère. Si deux demandes identiques arrivent presque en même temps (double clic avant que le bouton soit désactivé, par exemple), les deux peuvent voir « pas encore membre » et essayer d'insérer la même personne. Heureusement, la migration déclare table.unique(['user_id', 'conversation_id']) : la base refuse le doublon. La seconde demande échoue donc avec une erreur 500 au lieu d'un message clair, mais les données restent propres. C'est un bon exemple de l'intérêt d'une contrainte en base en plus de la vérification dans le code.

4. Personne ne peut quitter un groupe. Le contrôleur ne propose ni « quitter le groupe », ni « retirer un membre », ni « changer d'administrateur ». Un membre ajouté contre son gré ne peut pas sortir. Seule la suppression du compte retire quelqu'un d'un groupe (et transmet le rôle d'admin au membre le plus ancien).

Ce qui est bien fait, à retenir pour tes prochains projets :

• Le rôle est toujours relu en base avant une action sensible, et la différence entre 404 (pas membre) et 403 (membre mais pas admin) est respectée.

• La création est dans une transaction : jamais de groupe à moitié créé.

• Pour la suppression, la base d'abord, Cloudinary ensuite, et la cascade de PostgreSQL fait le ménage.

• Les nouveaux membres reçoivent le bon lastMessageId, et chaque type de personne (nouveaux membres, anciens membres, admin) reçoit le bon événement temps réel.
