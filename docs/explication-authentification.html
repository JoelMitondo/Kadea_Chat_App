Inscription, connexion et mot de passe oublié expliqués ligne par ligne

inscriptions_controller.ts · new_account_controller.ts · session_controller.ts · forgo_passwords_controller.ts · validateurs · app/mails/* · views/emails/* · pages/auth/* · resources/js/auth et utilitaires

Ce fichier suit les trois parcours d'une personne qui n'est pas encore connectée : créer un compte (en deux étapes, avec confirmation de l'e-mail), se connecter / se déconnecter, et retrouver l'accès avec un mot de passe oublié.

L'idée qui relie tout : un lien envoyé par e-mail prouve que la personne a accès à cette boîte. Le lien contient un code secret de 25 caractères. Ce code est envoyé en clair dans l'e-mail, mais la base n'en garde qu'une version hachée, comme un mot de passe. Pour vérifier un lien, on compare le code reçu au hash.

Les modèles Inscription et ForgoPassword sont vides (export default class Inscription extends InscriptionSchema {}) : leurs colonnes sont décrites dans database/schema.ts, généré à partir des migrations. L'e-mail est unique dans les deux tables : une seule demande en attente par adresse.

Pourquoi une table inscriptions séparée ? Le commentaire de new_account_controller.ts l'explique : le vrai compte n'est créé qu'après le clic sur le lien. Tant que l'e-mail n'est pas confirmé, il n'existe aucune ligne dans users, donc il est impossible de se connecter. Les demandes abandonnées ne polluent pas la table des comptes.

2. Le modèle User et withAuthFinder

import hash from '@adonisjs/core/services/hash'
import { compose } from '@adonisjs/core/helpers'
import { withAuthFinder } from '@adonisjs/auth/mixins/lucid'

export default class User extends compose(UserSchema, withAuthFinder(hash)) {
  @hasMany(() => Conversation, { foreignKey: 'createdById' })
  declare createdConversations: HasMany<typeof Conversation>
  ...
}
  • compose(UserSchema, withAuthFinder(hash)) : un « mixin ». La classe hérite des colonnes de UserSchema et reçoit en plus les capacités de withAuthFinder. Une classe JavaScript ne peut hériter que d'une seule classe, et compose permet d'en empiler plusieurs.
  • Ce que withAuthFinder ajoute, d'après le commentaire du fichier :
    1. User.verifyCredentials(email, password) : cherche l'utilisateur par e-mail et compare le mot de passe à son hash.
    2. Le hachage automatique : avant chaque enregistrement, si password a changé, il est remplacé par son hash (scrypt, voir config/hash.ts). C'est pourquoi le code écrit simplement user.password = payload.password, sans jamais appeler hash.make pour un mot de passe.
  • Les relations (messages, conversations, participations, blocksInitiated…) permettent de naviguer d'un utilisateur vers ses données. Elles ne servent pas dans ce lot.

Le validateur

const email = () => vine.string().email().maxLength(254)
const name = () => vine.string().trim().minLength(2).maxLength(50)

export const inscriptionValidator = vine.create({
  first_name: name(),
  last_name: name(),
  email: email().unique({ table: 'users', column: 'email' }),
  email_confirmation: email().sameAs('email'),
  birth_date: vine.date(),

  • const email = () => ... : une petite fonction qui fabrique la règle. On l'appelle deux fois (email()), et chaque appel crée une règle neuve. Réutiliser le même objet pour deux champs pourrait mélanger leurs réglages.
  • .email() vérifie le format. maxLength(254) est la longueur maximale d'une adresse e-mail selon la norme.
  • .unique({ table: 'users', column: 'email' }) fait une requête en base. Si un compte existe déjà avec cet e-mail, la validation échoue. On ne peut pas créer deux comptes avec la même adresse.
  • sameAs('email') : la confirmation doit être identique. Ça évite une faute de frappe qui enverrait le lien chez quelqu'un d'autre.
  • vine.date() vérifie que c'est une vraie date. Grâce à start/validator.ts, elle devient un DateTime de Luxon.

  • Pourquoi ? Le commentaire l'explique : l'e-mail est unique dans inscriptions.   • Si l'envoi de l'e-mail échoue (Brevo indisponible, clé invalide), l'erreur est notée dans les logs et la réponse est une 500 avec un message clair. L'inscription reste en base : un nouvel essai la remplacera grâce à updateOrCreate.

4. Les e-mails : app/mails et views/emails

La classe de l'e-mail

import { BaseMail } from '@adonisjs/mail'

export default class ConfirmationEmailMail extends BaseMail {
  subject = 'Confirmation de votre adresse e-mail - Kadea Chat'

  constructor(
    private recipient: { email: string; fullName: string },
    private activationLink: string,
    private expiresAt: string
  ) {
    super()
  }

  prepare() {
    this.message.to(this.recipient.email).htmlView('emails/confirmation_email', {
      fullName: this.recipient.fullName,
      email: this.recipient.email,
      activationLink: this.activationLink,
      expiresAt: this.expiresAt,
    })
  }
}
  • Une classe par e-mail, qui hérite de BaseMail. Le contrôleur n'a qu'à écrire mail.send(new ConfirmationEmailMail(...)).
  • subject : l'objet de l'e-mail.
  • private recipient: ... dans le constructeur est un raccourci de TypeScript : il déclare la propriété et la remplit en une fois. Sans lui, il faudrait écrire this.recipient = recipient. super() appelle le constructeur de BaseMail, ce qui est obligatoire dans une classe qui hérite.
  • prepare() est appelée par AdonisJS au moment de l'envoi. Elle fixe le destinataire (to) et le contenu HTML, fabriqué avec une vue Edge, comme une page.
  • L'expéditeur n'est pas écrit ici : il vient de config/mail.ts (MAIL_FROM_ADDRESS, MAIL_FROM_NAME).
  • ReinitialisationMotDePasseMail est construite exactement pareil, avec resetLink et la vue emails/reinitialisation_mot_de_passe.

La vue de l'e-mail

{{-- Les {{ }} échappent le HTML : un nom contenant des balises (<script>, <a>...)
     s'affiche comme du texte et ne s'exécute jamais. --}}
<div style="font-family: Arial, sans-serif; color: #333; line-height: 1.6;">
  <h2>Bonjour {{ fullName }},</h2>
  ...
  <a href="{{ activationLink }}" style="background-color: #2e7d32; ...">Confirmer mon e-mail</a>
  ...
</div>
  • Les styles sont écrits dans chaque balise (style="...") : beaucoup de logiciels de messagerie ignorent les feuilles de style. C'est la règle pour tout e-mail HTML.
  • L'échappement, rappelé par le commentaire : {{ fullName }} transforme < en &lt;. Quelqu'un qui s'inscrirait avec le nom <a href="piege">Cliquez</a> ne pourrait pas glisser un faux lien dans l'e-mail. C'était un des correctifs de sécurité P0.

config/mail.ts

default: env.get('MAIL_MAILER'),

5. Inscription, étape 2 : new_account_controller.ts

La personne clique sur le lien reçu. Le commentaire en tête rappelle l'essentiel : le lien prouve que l'adresse existe, et le vrai compte n'est créé qu'ici.

L'outil commun : chercheInscription

private async chercheInscription(id: string, code: string): Promise<
  | { error: null; inscription: Inscription }
  | { error: 'signupLinkInvalid' | 'signupLinkExpired'; inscription: null }
> {

Le type de retour est une union discriminée. La fonction renvoie soit { error: null, inscription }, soit { error: '...', inscription: null }. Après if (result.error) { return ... }, TypeScript sait que result.inscription n'est pas null. Le nom de l'erreur est aussi une clé de ERROR_PAGES, ce qui permet d'écrire ERROR_PAGES[result.error].

  const inscriptionId = Number(id)
  if (!Number.isInteger(inscriptionId) || inscriptionId <= 0) {
    return { error: 'signupLinkInvalid', inscription: null }
  }

  const inscription = await Inscription.find(inscriptionId)
  if (!inscription) {
    return { error: 'signupLinkInvalid', inscription: null }
  }
  • Vérifier l'identifiant à la main : cette route n'a pas de matcher ID_NUMERIQUE. Le commentaire l'explique : sans ce contrôle, /signup/abc/… ferait planter PostgreSQL (erreur 500). Number.isInteger refuse NaN, 1.5, etc.
  • Inscription.find(id) renvoie la ligne ou null. Contrairement à findOrFail, ça permet d'afficher une page d'erreur adaptée, au lieu de la 404 générique.
  const isValid = await hash.verify(inscription.codeAleatoire, code)
  if (!isValid) {
    return { error: 'signupLinkInvalid', inscription: null }
  }

  if (DateTime.now() > inscription.expiredAt!) {
    await inscription.delete()
    return { error: 'signupLinkExpired', inscription: null }
  }

  return { error: null, inscription }
}
  • hash.verify(hashStocké, codeReçu) refait le calcul et compare. On ne peut pas « déhacher » un hash, seulement vérifier qu'un code donne le même résultat.
  • Lien expiré : on supprime la demande au passage, pour faire le ménage en base. Le ! après expiredAt dit à TypeScript que la valeur n'est pas vide. Une migration l'a rendue obligatoire (alter_expired_at_not_null).
  • Trois cas d'erreur, deux pages : identifiant absurde, ligne introuvable ou mauvais code donnent tous « lien invalide ». On ne dit pas à un curieux si l'identifiant existe.

6. Connexion et déconnexion : session_controller.ts

async donnePageConnexion({ view }: HttpContext) {
  return view.render('pages/auth/login')
}

async connecte({ request, auth, response }: HttpContext) {
  const { email, password } = await request.validateUsing(loginValidator)
  const user = await User.verifyCredentials(email, password)

  await auth.use('web').login(user)
  response.redirect().toRoute('messages')
}
  • loginValidator : { email: email(), password: password() }, un e-mail valide et un mot de passe de 8 à 50 caractères.
  • User.verifyCredentials(email, password) vient de withAuthFinder. Elle cherche l'utilisateur par e-mail et compare le mot de passe à son hash. En cas d'échec (e-mail inconnu ou mauvais mot de passe), elle lance E_INVALID_CREDENTIALS. Elle ne dit volontairement pas lequel des deux est faux, et elle prend le même temps dans les deux cas : un attaquant ne peut pas découvrir quels e-mails sont inscrits.
  • Ce que voit l'utilisateur en cas d'échec : le formulaire de connexion est un formulaire classique (pas data-ajax). AdonisJS garde les champs tapés sauf le mot de passe (flashExcept), range le message dans le flash error et renvoie sur la page précédente. Le message, traduit dans handler.ts (« Adresse e-mail ou mot de passe incorrect. »), s'affiche en notification grâce à components/toasts.edge. L'e-mail reste rempli.
  • auth.use('web').login(user) range l'identifiant de l'utilisateur dans la session. AdonisJS régénère aussi l'identifiant de session à ce moment. Ça protège contre la « fixation de session » : un attaquant qui aurait imposé un cookie de session avant la connexion ne peut pas le réutiliser après.
  • 5 essais par minute au plus, grâce à limiteConnexion sur la route.
async deconnecte({ auth, response }: HttpContext) {
  await auth.use('web').logout()
  response.redirect().toRoute('session.create')
}

logout() retire l'utilisateur de la session, puis redirige vers la page de connexion (la route nommée session.create, c'est-à-dire GET /login). C'est un POST protégé par CSRF, donc un lien piégé ne peut pas te déconnecter.

7. Mot de passe oublié : forgo_passwords_controller.ts

Le commentaire en tête décrit les 3 étapes : donner son e-mail, cliquer sur le lien, choisir un nouveau mot de passe. Le lien ne sert qu'une fois.

Les validateurs

export const forgoPassewordValidator = vine.create({ email: email() })

export const newPassewordValidator = vine.create({
  password: password().confirmed(),
})

confirmed() exige un champ password_confirmation identique dans le formulaire. Le validateur a ses propres messages en français (« Les deux mots de passe ne correspondent pas. »).

Étape 1 : enregistreDemandeReinitialisation

  const user = await User.findBy('email', email)

    const expiration = DateTime.now().plus({ hours: 1 })

  • updateOrCreate : une nouvelle demande remplace la précédente, et l'ancien lien cesse de fonctionner.
    try {

La même réponse, que le compte existe ou non. Le commentaire l'explique : on ne révèle pas quels e-mails sont inscrits. Sinon, n'importe qui pourrait tester une liste d'adresses pour savoir qui utilise Kadea Chat. C'est pourquoi le message commence par « Si cette adresse correspond à un compte… ».

L'outil commun : chercheDemandeValide

private async chercheDemandeValide(id: string, code: string) {
  const requestId = Number(id)
  if (!Number.isInteger(requestId) || requestId <= 0) {
    return null
  }
  const recuperation = await ForgoPassword.find(requestId)
  if (!recuperation) {
    return null
  }
  if (recuperation.expiredAt! < DateTime.now()) {
    await recuperation.delete()
    return null
  }
  const isValid = await hash.verify(recuperation.codeAleatoire, code)
  return isValid ? recuperation : null
}

La même logique que chercheInscription : identifiant valide, ligne trouvée, pas expirée (supprimée au passage sinon), code correct. Elle renvoie la demande, ou null dans tous les cas d'échec. On ne distingue pas les erreurs.

Étape 3 : enregistreNouveauMotDePasse

async enregistreNouveauMotDePasse({ request, response, auth, params }: HttpContext) {
  const payload = await request.validateUsing(newPassewordValidator)

  const recuperation = await this.chercheDemandeValide(params.id, params.code)
  if (!recuperation) {
    return response.badRequest({ message: 'Lien de récupération invalide ou expiré.' })
  }

  const user = await User.findOrFail(recuperation.userId)
  user.password = payload.password
  await user.save()

  await recuperation.delete()

  await auth.use('web').login(user)

  if (request.accepts(['html', 'json']) === 'json') {
    return response.ok({ message: 'Votre mot de passe a été modifié.' })
  }
  return response.redirect().toRoute('messages')
}
  • Le lien est revérifié au moment de l'envoi, pas seulement à l'affichage de la page.
  • user.password = payload.password puis save() : withAuthFinder hache le nouveau mot de passe tout seul.
  • recuperation.delete() : le lien ne sert qu'une fois.
  • Connexion directe, puis le script redirige vers /messages grâce à l'attribut data-redirect du formulaire.

10. Ce qui a été remarqué

Ce qui est bien fait, à mettre en avant :

• Le compte n'est créé qu'après la confirmation de l'e-mail.

• Les codes des liens sont tirés avec crypto, stockés hachés, utilisables une seule fois et limités dans le temps (48 h et 1 h).

• Le mot de passe oublié ne révèle pas quels e-mails sont inscrits, et la connexion ne dit pas lequel de l'e-mail ou du mot de passe est faux.

• Les cas limites sont gérés proprement : nouvelle inscription avec le même e-mail, compte créé entre-temps, lien expiré, identifiant non numérique. Chacun a sa page d'erreur au lieu d'une erreur 500.

• Les mots de passe sont hachés automatiquement par withAuthFinder, la session est régénérée à la connexion, et les e-mails échappent les noms.

1. L'inscription révèle si un e-mail a déjà un compte. La règle .unique({ table: 'users' }) renvoie une erreur « déjà utilisé » pour une adresse inscrite, alors que le mot de passe oublié fait tout pour ne pas le révéler. C'est un compromis courant, au profit du confort de l'utilisateur. Pour être cohérent, on pourrait répondre toujours « Un e-mail vous a été envoyé », et envoyer à l'adresse déjà inscrite un e-mail « Vous avez déjà un compte ».

2. La vérification en direct refuse les noms avec une apostrophe. La regex /^[a-zA-ZÀ-ÿ\s\-]+$/ n'accepte pas '. Des noms courants comme N'Diaye, N'Golo ou O'Brien affichent une erreur, et le bouton « Créer mon compte » reste caché. Le serveur, lui, les accepte. Il suffirait d'ajouter ' (et ’) dans la regex.

3. Le validateur de création de compte accepte avatar_url et bio, que le formulaire signup.edge n'envoie pas. Quelqu'un qui modifierait la requête pourrait mettre l'adresse de n'importe quelle image comme photo de profil. La CSP l'empêcherait de s'afficher, puisque seuls Cloudinary et i.ibb.co sont autorisés. Le plus propre est de retirer ces deux champs du validateur et de laisser la photo se gérer depuis le profil.

4. Pas de confirmation du mot de passe à la création du compte, alors que le mot de passe oublié et les paramètres en demandent une. Une faute de frappe oblige à passer par « mot de passe oublié ». On pourrait ajouter .confirmed() et un champ password_confirmation.

5. Changer de mot de passe ne déconnecte pas les autres appareils. Après « mot de passe oublié », une session ouverte ailleurs, par exemple par quelqu'un qui aurait volé le mot de passe, reste valable jusqu'à son expiration (2 heures). Avec des sessions stockées en base, on pourrait les supprimer toutes.

6. Un petit écart de temps de réponse : le mot de passe oublié envoie un e-mail seulement si le compte existe. La réponse est donc un peu plus lente dans ce cas, et un attaquant patient pourrait le mesurer. Envoyer l'e-mail en arrière-plan (file d'attente) ferait disparaître cet écart. C'est un point avancé, rarement traité dans un projet de formation.
