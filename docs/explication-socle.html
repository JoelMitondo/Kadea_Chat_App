Le socle de Kadea Chat expliqué ligne par ligne

Comment une requête traverse l'application · adonisrc.ts, start/*, app/middleware/*, app/policies/*, app/exceptions/handler.ts, app/services/error_page.ts, config/*

Les contrôleurs expliqués dans les autres fichiers ne travaillent jamais seuls. Avant eux, la requête est lue, la session chargée, la sécurité vérifiée, l'utilisateur reconnu. Après eux, ou à leur place en cas d'erreur, une réponse propre est fabriquée. Ce fichier explique tout ce « tuyau » autour des contrôleurs.

L'idée à retenir : une requête traverse une suite de middlewares, comme des postes de contrôle à la file. Chaque poste fait son travail puis appelle next() pour passer au suivant. Il peut aussi arrêter la requête (par exemple, rediriger vers /login). Le contrôleur est le dernier poste.

1. Le trajet d'une requête, en un schéma

Navigateur : DELETE /messages/42  (cookie de session + jeton CSRF)
   │
   ├─ MIDDLEWARES SERVEUR (toutes les requêtes, même vers une adresse inconnue)
   │    container_bindings → static (fichiers de public/) → vite (fichiers CSS/JS)
   │
   ├─ LE ROUTEUR cherche une route qui correspond (start/routes.ts)
   │    aucune ? → erreur E_ROUTE_NOT_FOUND → handler → page 404
   │
   ├─ MIDDLEWARES DU ROUTEUR (toutes les requêtes qui ont une route)
   │    bodyparser → session → shield (CSRF, en-têtes) → initialize_auth
   │    → silent_auth (qui est connecté ?) → initialize_bouncer
   │
   ├─ MIDDLEWARES NOMMÉS de la route (choisis route par route)
   │    auth (connecté, sinon /login) ou guest · limiteur d'essais
   │
   ├─ LE CONTRÔLEUR : MessagesController.supprimeMessage
   │    validation, participation (404), policy (403), base de données
   │
   └─ RÉPONSE : JSON ou HTML
        en cas d'erreur à N'IMPORTE QUELLE étape → app/exceptions/handler.ts

2. Le démarrage : adonisrc.ts, les alias et les fichiers générés

Les « preloads » d'adonisrc.ts

preloads: [
  () => import('#start/routes'),
  () => import('#start/kernel'),
  () => import('#start/validator'),
  () => import('#start/view'),
  {
    file: () => import('#start/transmit'),
    environment: ['web'],
  },
],
  • Un preload est un fichier exécuté une seule fois, au démarrage du serveur, avant la première requête. C'est là qu'on déclare les routes, les middlewares, la configuration de VineJS et d'Edge.
  • () => import(...) : une fonction qui charge le fichier quand AdonisJS l'appelle (import « paresseux »).
  • environment: ['web'] : start/transmit.ts n'est chargé que quand l'application tourne comme serveur web. Il ne l'est pas pour les commandes node ace (migrations, seeders…) : inutile de suivre la présence en ligne pendant une migration, et il remettrait is_online à faux à chaque commande.

Les alias #… de package.json

"imports": {
  "#controllers/*": "./app/controllers/*.js",
  "#models/*": "./app/models/*.js",
  "#services/*": "./app/services/*.js",
  "#policies/*": "./app/policies/*.js",
  "#generated/*": "./.adonisjs/server/*.js",
  "#start/*": "./start/*.js",
  ...
}
  • C'est une fonction standard de Node.js : les « subpath imports ». Une importation qui commence par # est traduite en chemin. #services/chat_service devient ./app/services/chat_service.js.
  • Avantage : le même import fonctionne depuis n'importe quel dossier. Plus de '../../service/chat_service.ts' qui casse quand on déplace un fichier ou qu'on renomme un dossier. Le renommage app/service → app/services n'a demandé de changer que cette table.
  • .js alors que les fichiers sont en .ts : c'est le nom qu'aura le fichier une fois compilé. En développement, le chargeur de TypeScript fait la correspondance.

Les fichiers générés : #generated/controllers et #generated/policies

// .adonisjs/server/controllers.ts — "This file is automatically generated. DO NOT EDIT manually"
export const controllers = {
  Conversations: () => import('#controllers/conversations_controller'),
  Groups: () => import('#controllers/groups_controller'),
  ...
}

AdonisJS parcourt app/controllers et app/policies et écrit cette liste tout seul. C'est pourquoi start/routes.ts peut écrire [controllers.Groups, 'donneGroupe'] : controllers.Groups vient de ce fichier. Chaque contrôleur n'est chargé en mémoire qu'à la première requête qui en a besoin, ce qui accélère le démarrage.

3. start/env.ts : les variables d'environnement

export default await Env.create(new URL('../', import.meta.url), {
  NODE_ENV: Env.schema.enum(['development', 'production', 'test'] as const),
  PORT: Env.schema.number(),
  HOST: Env.schema.string({ format: 'host' }),
  APP_KEY: Env.schema.secret(),
  APP_URL: Env.schema.string({ format: 'url', tld: false }),
  SESSION_DRIVER: Env.schema.enum(['cookie', 'memory', 'database'] as const),
  DB_HOST: Env.schema.string(),
  DB_PASSWORD: Env.schema.string.optional(),
  BREVO_API_KEY: Env.schema.string(),
  CLOUDINARY_API_SECRET: Env.schema.secret(),
  LIMITER_STORE: Env.schema.enum.optional(['database', 'memory'] as const),
  ...
})
  • Le rôle : lire le fichier .env (ou les variables du serveur, sur Render) et vérifier chaque valeur au démarrage. S'il manque DB_HOST ou si PORT n'est pas un nombre, le serveur refuse de démarrer avec un message clair. C'est bien mieux qu'un plantage mystérieux à la première requête.
  • new URL('../', import.meta.url) : le dossier où chercher le .env, c'est-à-dire la racine du projet (un niveau au-dessus de start/).
  • await au niveau du module : autorisé dans les modules modernes. Tant que l'environnement n'est pas validé, aucun fichier qui importe #start/env ne continue.
  • enum([...] as const) : seules ces valeurs sont acceptées. as const permet à TypeScript de connaître la liste exacte : env.get('NODE_ENV') a le type 'development' | 'production' | 'test'.
  • secret() : pour APP_KEY et CLOUDINARY_API_SECRET. La valeur est enveloppée dans un objet Secret. Si on l'affiche par erreur dans un log, on voit [redacted] au lieu de la clé. Pour s'en servir, il faut appeler .release() (vu dans le service Cloudinary).
  • optional() : la variable peut manquer. DB_PASSWORD (base locale sans mot de passe) et LIMITER_STORE (valeur par défaut 'database' dans config/limiter.ts).
  • APP_KEY est la clé qui chiffre et signe les cookies, dont celui de la session. Si elle fuite, quelqu'un pourrait fabriquer un faux cookie de session.

4. start/kernel.ts : la liste des middlewares

server.errorHandler(() => import('#exceptions/handler'))

Toute erreur levée pendant une requête, où qu'elle soit, arrive dans ce fichier. Il est expliqué au point 11.

server.use([
  () => import('#middleware/container_bindings_middleware'),
  () => import('@adonisjs/static/static_middleware'),
  () => import('@adonisjs/vite/vite_middleware'),
])

Les middlewares serveur s'exécutent pour toutes les requêtes, même vers une adresse qui n'a pas de route. C'est indispensable pour static : /favicon.ico ou une image de public/ n'ont pas de route, mais doivent être servis.

router.use([
  () => import('@adonisjs/core/bodyparser_middleware'),
  () => import('@adonisjs/session/session_middleware'),
  () => import('@adonisjs/shield/shield_middleware'),
  () => import('@adonisjs/auth/initialize_auth_middleware'),
  () => import('#middleware/silent_auth_middleware'),
  () => import('#middleware/initialize_bouncer_middleware'),
])

Les middlewares du routeur s'exécutent pour toutes les requêtes qui ont une route. Le commentaire du fichier le dit : l'ordre compte.

  1. On lit d'abord le corps de la requête (bodyparser).
  2. Puis la session (session) : elle lit le cookie.
  3. Puis la sécurité (shield). Le jeton CSRF attendu est rangé dans la session, et le jeton envoyé dans le corps. Il faut donc les deux avant.
  4. Puis l'authentification (initialize_auth, silent_auth) : « qui est connecté ? » se lit dans la session.
  5. Enfin Bouncer (initialize_bouncer), qui a besoin de connaître l'utilisateur.
export const middleware = router.named({
  guest: () => import('#middleware/guest_middleware'),
  auth: () => import('#middleware/auth_middleware'),
})

Les middlewares nommés ne s'exécutent que sur les routes qui les demandent, avec .use(middleware.auth()) dans start/routes.ts. export permet à routes.ts de les importer avec import { middleware } from '#start/kernel'.

5. Chaque middleware, dans l'ordre

La forme commune d'un middleware

export default class UnMiddleware {
  async handle(ctx: HttpContext, next: NextFn) {
    // ... travail AVANT le contrôleur ...
    return next()       // passe au middleware suivant (puis, au bout, au contrôleur)
  }
}

ctx est le contexte de la requête, le même objet que reçoit le contrôleur. next() lance la suite de la chaîne. Ne pas l'appeler arrête la requête : c'est ce que font auth et guest quand ils redirigent.

container_bindings_middleware.ts

handle(ctx: HttpContext, next: NextFn) {
  ctx.containerResolver.bindValue(HttpContext, ctx)
  ctx.containerResolver.bindValue(Logger, ctx.logger)
  return next()
}

AdonisJS a un « conteneur » capable de fournir automatiquement des objets aux classes qui les demandent (injection de dépendances). Ce middleware lui dit : « pour cette requête, si quelqu'un demande HttpContext, donne ce ctx ; s'il demande Logger, donne le logger de la requête ». Kadea Chat ne s'en sert pas directement, mais Bouncer l'utilise (setContainerResolver, plus bas). Ce fichier fait partie du squelette d'AdonisJS.

static_middleware et vite_middleware (fournis par AdonisJS)

  • static sert les fichiers du dossier public/ tels quels. Sa config, config/static.ts, active etag et lastModified : le navigateur peut demander « ce fichier a-t-il changé ? » et recevoir un simple « non » (code 304) au lieu de tout retélécharger. dotFiles: 'ignore' refuse de servir les fichiers cachés comme .env.
  • vite sert le CSS et le JavaScript de resources/. En développement, il passe par le serveur Vite, qui recharge la page à chaud. En production, il sert les fichiers compilés.

bodyparser_middleware et config/bodyparser.ts

form:      { convertEmptyStringsToNull: true, trimWhitespaces: true, ... },
json:      { convertEmptyStringsToNull: true, trimWhitespaces: true, ... },
multipart: { autoProcess: true, ..., limit: '20mb', types: ['multipart/form-data'] },
  • Il lit le corps de la requête (formulaire classique, JSON envoyé par fetch, ou fichier envoyé) et le range dans request. C'est grâce à lui que request.validateUsing(...) trouve les données.
  • trimWhitespaces : " jo " devient "jo", pour tous les champs, avant même la validation.
  • convertEmptyStringsToNull : un champ laissé vide ("") devient null. C'est pour ça qu'une bio vide est enregistrée null en base, et pas comme une chaîne vide.
  • multipart concerne les envois de fichiers. autoProcess enregistre le fichier dans un dossier temporaire : c'est le tmpPath que le service Cloudinary envoie ensuite. limit: '20mb' est la taille maximale de tout l'envoi. Au-delà, l'erreur E_REQUEST_ENTITY_TOO_LARGE (code 413) est levée avant même le contrôleur. La limite de 10 Mo par fichier est vérifiée plus tard, par le validateur des messages.

session_middleware et config/session.ts

cookieName: 'adonis-session',
clearWithBrowser: false,
age: '2h',
cookie: { path: '/', httpOnly: true, secure: app.inProduction, sameSite: 'lax' },
store: env.get('SESSION_DRIVER'),
stores: { cookie: stores.cookie(), database: stores.database() },
  • La session est une petite mémoire liée à un navigateur, d'une requête à l'autre. Elle contient l'identifiant de l'utilisateur connecté, les messages flash (« Le groupe a été créé ») et le jeton CSRF.
  • store : où ces données sont rangées. Avec cookie, elles sont dans le cookie lui-même, chiffré avec APP_KEY. Avec database, le cookie ne contient qu'un identifiant et les données sont en base.
  • age: '2h' : la session expire après 2 heures, et l'utilisateur est déconnecté. clearWithBrowser: false : fermer le navigateur ne la supprime pas avant ce délai.
  • httpOnly: true : le JavaScript de la page ne peut pas lire ce cookie. Même un script malveillant injecté ne pourrait pas voler la session.
  • secure: app.inProduction : en production, le cookie n'est envoyé qu'en HTTPS. En local, on travaille en HTTP, d'où la condition.
  • sameSite: 'lax' : le navigateur n'envoie pas le cookie avec un formulaire posté depuis un autre site. C'est une première barrière contre les attaques CSRF, en plus du jeton.

shield_middleware

Il applique toute la configuration de config/shield.ts, assez importante pour avoir sa propre section : point 6.

initialize_auth_middleware et silent_auth_middleware.ts

// silent_auth_middleware.ts
async handle(ctx: HttpContext, next: NextFn) {
  await ctx.auth.check()
  return next()
}
  • initialize_auth (fourni par AdonisJS) crée ctx.auth pour la requête, avec le « guard » web défini dans config/auth.ts (authentification par session, utilisateurs du modèle User).
  • silent_auth appelle ctx.auth.check() : il regarde dans la session s'il y a un utilisateur connecté et, si oui, le charge dans ctx.auth.user. Il ne bloque jamais : connecté ou non, la requête continue.
  • Pourquoi ? Pour que les pages publiques (l'accueil, une page 404) sachent quand même si tu es connecté. C'est ce qui permet à l'accueil d'afficher « Mes messages » au lieu de « Se connecter », sans requête supplémentaire du navigateur.

initialize_bouncer_middleware.ts

ctx.bouncer = new Bouncer(
  () => ctx.auth.user || null,
  abilities,
  policies
).setContainerResolver(ctx.containerResolver)

if ('view' in ctx) {
  ctx.view.share(ctx.bouncer.edgeHelpers)
}
  • Crée ctx.bouncer pour la requête. C'est l'objet que les contrôleurs utilisent : bouncer.with(GroupPolicy).authorize(...).
  • () => ctx.auth.user || null : une fonction qui donne l'utilisateur, et non l'utilisateur lui-même. Bouncer ne la lit qu'au moment de vérifier une règle, donc il voit toujours l'utilisateur à jour.
  • abilities vient de app/abilities/main.ts. Le fichier est vide (export {}), et son commentaire explique pourquoi : toutes les règles de Kadea Chat portent sur une ressource (un message, un groupe), elles sont donc dans des policies.
  • policies vient de #generated/policies, la liste générée automatiquement à partir de app/policies/.
  • ctx.view.share(...) rend Bouncer utilisable dans les vues Edge (par exemple @can(...)). Le if ('view' in ctx) évite une erreur pour les requêtes sans vue.
  • Le bloc declare module en bas du fichier ajoute la propriété bouncer au type HttpContext. Sans lui, TypeScript refuserait { bouncer } dans les paramètres d'un contrôleur.

auth_middleware.ts (nommé : middleware.auth())

redirectTo = '/login'

async handle(ctx, next, options: { guards?: (keyof Authenticators)[] } = {}) {
  await ctx.auth.authenticateUsing(options.guards, { loginRoute: this.redirectTo })
  return next()
}
  • authenticateUsing exige un utilisateur connecté. S'il n'y en a pas, elle lance l'erreur E_UNAUTHORIZED_ACCESS, et next() n'est jamais atteint.
  • Pour une page normale, cette erreur se transforme en redirection vers /login (loginRoute). Pour un fetch, le handler la transforme en réponse JSON 401, avec « Votre session a expiré… ». notifications.js affiche ce message puis renvoie vers /login après 2 secondes.
  • options.guards permettrait de choisir une autre méthode de connexion. Kadea Chat n'en a qu'une (web), donc le paramètre est vide.

guest_middleware.ts (nommé : middleware.guest())

redirectTo = '/'

for (let guard of options.guards || [ctx.auth.defaultGuard]) {
  if (await ctx.auth.use(guard).check()) {
    ctx.session.reflash()
    return ctx.response.redirect(this.redirectTo, true)
  }
}
return next()
  • L'inverse d'auth : une personne déjà connectée n'a rien à faire sur /login, /register ou « mot de passe oublié ». Elle est renvoyée vers l'accueil.
  • ctx.session.reflash() : garde les messages flash pour la page suivante. Sans lui, un message flash serait « consommé » par cette redirection et n'apparaîtrait jamais.
  • redirect(this.redirectTo, true) : le true recopie la « query string » (?…) dans l'adresse de destination.

6. config/shield.ts : CSRF, CSP et en-têtes de sécurité

CSRF : le jeton secret des formulaires

csrf: {
  enabled: true,
  exceptRoutes: [],
  enableXsrfCookie: false,
  methods: ['POST', 'PUT', 'PATCH', 'DELETE'],
},
  • L'attaque CSRF : un site piégé contient un formulaire caché qui envoie POST /settings/delete-account vers Kadea Chat. Si tu es connecté, ton navigateur joint ton cookie de session tout seul, et la requête semblerait venir de toi.
  • La parade : chaque envoi (POST, PUT, PATCH, DELETE) doit contenir un jeton secret rangé dans ta session. Le site piégé ne peut pas le connaître. Une requête sans le bon jeton est refusée avec l'erreur E_BAD_CSRF_TOKEN.
  • Où est le jeton dans Kadea Chat ?
    • Dans les formulaires classiques : {{ csrfField() }} ajoute un champ caché _csrf.
    • Pour le JavaScript : <meta name="csrf-token" content="{{ csrfToken }}"> dans le layout. realtime.js et les autres scripts le lisent et l'envoient dans l'en-tête X-CSRF-TOKEN.
  • GET n'est pas protégé : c'est normal, une requête GET ne doit jamais rien modifier. C'est une règle à respecter dans les routes.
  • exceptRoutes: [] : aucune route n'est exemptée. Les routes de Transmit (/__transmit/subscribe…) reçoivent donc aussi le jeton, d'où sa lecture dans realtime.js.

CSP : la liste des sources autorisées

csp: {
  enabled: true,
  directives: {
    defaultSrc: [`'self'`],
    scriptSrc: [`'self'`, '@nonce'],
    styleSrc: [`'self'`, `'unsafe-inline'`],
    imgSrc: [`'self'`, 'data:', 'blob:', 'https://res.cloudinary.com', 'https://i.ibb.co'],
    connectSrc: [`'self'`, ...(app.inProduction ? [] : ['ws://localhost:24678'])],
    fontSrc: [`'self'`, 'data:'],
    objectSrc: [`'none'`],
    baseUri: [`'self'`],
    formAction: [`'self'`],
    frameAncestors: [`'none'`],
  },
  reportOnly: false,
},

La Content Security Policy est un en-tête envoyé avec chaque page. Elle dit au navigateur d'où il a le droit de charger chaque type de ressource. Si un attaquant arrivait à glisser <script>…</script> dans un message, le navigateur refuserait de l'exécuter. C'est une seconde ligne de défense, derrière l'échappement automatique d'Edge ({{ }}).

DirectiveValeurCe que ça veut dire
defaultSrc'self'Par défaut, seulement notre propre site.
scriptSrc'self', @nonceNos fichiers JS, et les scripts écrits dans la page seulement s'ils portent le nonce.
styleSrc'self', 'unsafe-inline'Notre CSS, et les attributs style="..." (délais d'animation, chargeur).
imgSrc…, Cloudinary, i.ibb.coLes photos et fichiers sur Cloudinary, le logo hébergé, et les images data: / blob: (aperçu d'une photo avant envoi).
connectSrc'self' (+ Vite en dev)fetch et le temps réel ne peuvent parler qu'à notre serveur. Même un script injecté ne pourrait pas envoyer des données ailleurs.
objectSrc'none'Aucun <object> / <embed> (anciens plugins).
baseUri'self'Interdit un <base href> injecté, qui redirigerait tous les liens relatifs.
formAction'self'Un formulaire ne peut être envoyé qu'à notre site.
frameAncestors'none'Aucun autre site ne peut afficher Kadea Chat dans une <iframe>.
  • Le nonce (@nonce) est un code aléatoire différent à chaque requête. Shield le place dans l'en-tête CSP et le rend disponible dans les vues sous le nom cspNonce. partials/head-script.edge l'utilise : <script nonce="{{ cspNonce }}">. Un script injecté par un attaquant ne connaît pas ce code, et il est bloqué.
  • Conséquence pour le code : les attributs comme onerror="..." ou onclick="..." sont des scripts en ligne sans nonce, donc interdits. C'est pourquoi head-script.edge remplace onerror par des attributs data-remove-on-error / data-hide-on-error et un seul écouteur d'événement.
  • ws://localhost:24678 en développement seulement : c'est la connexion du rechargement à chaud de Vite. Le ...(condition ? [] : [...]) ajoute l'élément au tableau seulement si on n'est pas en production.
  • reportOnly: false : la politique est appliquée. En mode « report only », le navigateur se contenterait de signaler les violations sans rien bloquer.

Les trois derniers en-têtes

xFrame: { enabled: true, action: 'DENY' },
hsts: { enabled: true, maxAge: '180 days' },
contentTypeSniffing: { enabled: true },
  • xFrame: DENY envoie X-Frame-Options: DENY, l'ancienne version de frameAncestors. Elle est gardée pour les vieux navigateurs. Elle protège du « clickjacking » : afficher Kadea Chat en transparence par-dessus un faux bouton.
  • hsts envoie Strict-Transport-Security. Une fois venu en HTTPS, le navigateur refusera le HTTP pour ce site pendant 180 jours, même si on tape http://.
  • contentTypeSniffing envoie X-Content-Type-Options: nosniff. Le navigateur respecte le type annoncé et ne « devine » pas qu'un fichier texte serait en fait un script.

7. start/routes.ts : le plan du site

Le commentaire en tête du fichier est un petit cours à lui seul : GET pour afficher, POST pour enregistrer, PUT pour modifier, DELETE pour supprimer ; :id est une valeur variable lue avec params.id ; .as('nom') donne un nom à la route.

Les imports et les matchers

import { middleware } from '#start/kernel'
import { controllers } from '#generated/controllers'
import router from '@adonisjs/core/services/router'
import transmit from '@adonisjs/transmit/services/main'
import { limiteConnexion, limiteEnvoiEmail, limiteMotDePasseActuel } from '#start/limiter'

const ID_NUMERIQUE = router.matchers.number()
const ID_UUID = router.matchers.uuid()
  • router.matchers.number() est une règle sur un paramètre d'adresse. Utilisée avec .where('id', ID_NUMERIQUE), la route ne correspond que si :id est fait de chiffres, et la valeur est convertie en nombre. Pour /groups/abc, aucune route ne correspond, donc 404. Sans ça, Number('abc') donnerait NaN et PostgreSQL une erreur 500.
  • router.matchers.uuid() fait la même chose pour les identifiants d'utilisateur (/users/:id/chat, /groups/:id/members/:userId).

Les routes publiques

router.get('/ping', [controllers.HealthChecks, 'verifieServeur']).as('health_checks.ping')
router.on('/').render('pages/home').as('home')
  • /ping renvoie { status: 'healthy', timestamp }. Le commentaire de health_checks_controller.ts l'explique : un robot UptimeRobot l'appelle toutes les 13 minutes, pour que le serveur gratuit de Render ne « s'endorme » pas après une période sans visite.
  • router.on('/').render('pages/home') est un raccourci pour une page qui n'a besoin d'aucun contrôleur : on affiche directement la vue. Grâce à silent_auth, la vue sait quand même si tu es connecté.

Les groupes de routes et leurs middlewares

router
  .group(() => {
    router.get('login', [controllers.Session, 'donnePageConnexion']).as('session.create')
    router.post('login', [controllers.Session, 'connecte']).as('session.store').use(limiteConnexion)
    ...
  })
  .use(middleware.guest())
  • router.group(() => { ... }) regroupe des routes pour leur appliquer quelque chose en une fois. Ici, .use(middleware.guest()) : toutes ces pages sont réservées aux visiteurs non connectés.
  • Le grand groupe suivant (profil, messages, groupes, utilisateurs, paramètres, recherche) porte .use(middleware.auth()) : il faut être connecté. C'est la protection principale de l'application, posée une seule fois pour des dizaines de routes. Oublier un contrôle dans un contrôleur ne peut pas exposer une page à un visiteur anonyme.
  • logout est dans un petit groupe auth à part : il faut être connecté pour se déconnecter, et c'est un POST (protégé par CSRF). Un simple lien piégé vers /logout ne peut donc pas te déconnecter.
  • /register (inscription) n'est pas dans le groupe guest. Une personne connectée pourrait donc ouvrir cette page, ce qui est sans danger.

.use(limite…) sur une route

Une route peut avoir ses propres middlewares. .use(limiteConnexion) sur POST /login limite le nombre d'essais. Les règles sont au point 8.

Les routes de Transmit

transmit.registerRoutes((route) => {
  route.middleware(middleware.auth())
})

Transmit ajoute trois routes : /__transmit/events (la connexion SSE), subscribe et unsubscribe. Pour chacune, on ajoute le middleware auth : une personne non connectée ne peut même pas ouvrir la connexion temps réel. La règle « chacun n'écoute que son propre canal » est ensuite dans start/transmit.ts (voir le fichier sur le temps réel).

8. start/limiter.ts et config/limiter.ts : limiter les essais

export const limiteConnexion = limiter.define('connexion', (ctx) => {
  const email = String(ctx.request.input('email', '')).toLowerCase()
  return limiter
    .allowRequests(5)
    .every('1 minute')
    .blockFor('5 minutes')
    .usingKey(`connexion_${ctx.request.ip()}_${email}`)
})
  • limiter.define(nom, fonction) crée un middleware de limitation. La fonction reçoit le contexte et décrit la règle.
  • allowRequests(5).every('1 minute') : 5 essais par minute.
  • blockFor('5 minutes') : au-delà, blocage de 5 minutes, même si la minute est passée. C'est ce qui rend la force brute (essayer des milliers de mots de passe) beaucoup trop lente.
  • usingKey(...) : ce qu'on compte. Ici, l'adresse IP et l'e-mail tapé. Quelqu'un qui se trompe sur son propre compte n'est pas bloqué pour un autre compte, et deux personnes derrière la même IP (une école) ne se bloquent pas entre elles. String(...) et toLowerCase() évitent de contourner la limite avec ANA@… au lieu de ana@….
export const limiteEnvoiEmail = limiter.define('envoi_email', (ctx) => {
  return limiter.allowRequests(5).every('15 minutes').usingKey(`email_${ctx.request.ip()}`)
})

export const limiteMotDePasseActuel = limiter.define('mot_de_passe_actuel', (ctx) => {
  return limiter.allowRequests(5).every('1 minute').blockFor('5 minutes')

  • limiteEnvoiEmail protège les routes qui envoient un e-mail (inscription, mot de passe oublié) : 5 envois par quart d'heure et par IP. Sans elle, un script pourrait épuiser le quota gratuit de Brevo ou inonder la boîte de quelqu'un.
  • limiteMotDePasseActuel protège les actions qui demandent le mot de passe actuel (changement, suppression du compte). La clé est le compte (ctx.auth.user?.id), ou l'IP à défaut. Quelqu'un qui a volé une session ouverte ne peut pas deviner le mot de passe pour supprimer le compte.

    httpError.message = httpError.response?.message || FORBIDDEN_MESSAGE
    httpError.status = httpError.response?.status || 403
  }
  • error: unknown : n'importe quoi peut être lancé en JavaScript, pas seulement une Error. as HttpError dit à TypeScript de le traiter comme une erreur HTTP. Les ?. protègent si ce n'en est pas une.
  • Étape 0 : pour un refus de policy, on prend le message écrit dans la policy (« Seul l'administrateur du groupe peut le supprimer. »), ou le message générique à défaut. Le statut devient 403.

  const frenchMessage = httpError?.code ? FRENCH_MESSAGES[httpError.code] : undefined
  if (frenchMessage) {
    httpError.message = frenchMessage
  }

Étape 1 : si le code de l'erreur est dans le dictionnaire, son message est remplacé par la version française. Une erreur sans code connu garde son message.

    return this.respondAsJson(httpError, ctx)

Mais fetch suit les redirections tout seul : il recevrait la page HTML de destination avec le code 200, et le script croirait que l'action a réussi. Pour un fetch, on répond donc toujours en JSON, avec le vrai code d'erreur.

Les deux méthodes privées

private isScriptRequest(ctx: HttpContext) {
  return (
    ctx.request.header('x-requested-with') === 'XMLHttpRequest' ||
    ctx.request.accepts(['html', 'json']) === 'json'
  )
}

Une requête vient du JavaScript si elle porte l'en-tête X-Requested-With (ajouté par les scripts de Kadea Chat), ou si le navigateur préfère le JSON au HTML (Accept: application/json). accepts([...]) renvoie le premier type de la liste que la requête accepte le mieux.

private respondAsJson(error: HttpError, ctx: HttpContext) {
  const code = error?.code

  if (code === 'E_BAD_CSRF_TOKEN') {
    return ctx.response.status(419).send({ message: error.message })
  }

  const status = error?.status && error.status >= 400 ? error.status : 500

  if (status >= 500) {
    const message = app.inProduction || !error?.message ? SERVER_ERROR_MESSAGE : error.message
    return ctx.response.status(status).send({ message })
  }

  return ctx.response
    .status(status)
    .send({ message: error.message, errors: [{ message: error.message }] })
}
  • CSRF : code 419. Ce n'est pas un code officiel, mais une convention (reprise de Laravel) pour « page expirée ». notifications.js le reconnaît et affiche « Votre session a expiré. Rechargez la page… ».
  • Le statut : celui de l'erreur s'il est valide (400 ou plus), sinon 500. Une erreur sans statut est un bug, donc une erreur serveur.
  • Erreur 500 en production : on n'envoie jamais le message technique (nom de table, requête SQL, chemin de fichier…). Ce serait une information précieuse pour un attaquant. On envoie un message générique. En développement, le vrai message aide à corriger.
  • Les autres erreurs (403, 404, 429…) : le message est envoyé deux fois, dans message et dans errors[0].message. Le second suit le même format que les erreurs de validation : le JavaScript n'a qu'une seule façon de lire une erreur (lireErreur), quelle qu'en soit l'origine.
async report(error: unknown, ctx: HttpContext) {
  return super.report(error, ctx)
}

report écrit l'erreur dans les journaux (logs). Elle n'est pas modifiée ici, on garde le comportement par défaut. C'est l'endroit où l'on brancherait un service de suivi d'erreurs.

14. Exemple complet : Jo essaie de supprimer un message d'Ana

Jo modifie la requête à la main pour envoyer DELETE /messages/42, alors que le message 42 appartient à Ana.

  1. container_bindings, static, vite : rien à faire, ce n'est pas un fichier.
  2. Le routeur trouve .delete('/messages/:id', ...). 42 est bien un nombre (ID_NUMERIQUE), et params.id vaut 42.
  3. bodyparser lit le corps de la requête.
  4. session déchiffre le cookie adonis-session.
  5. shield compare le jeton X-CSRF-TOKEN à celui de la session. Jo envoie la requête depuis sa propre page, donc le jeton est bon. Une page piégée sur un autre site aurait été arrêtée ici : 419.
  6. initialize_auth et silent_auth chargent Jo dans ctx.auth.user.
  7. initialize_bouncer crée ctx.bouncer pour Jo.
  8. auth (groupe de routes) : Jo est connecté, on continue. Un visiteur anonyme aurait reçu un 401 JSON.
  9. supprimeMessage : Message.findOrFail(42) trouve le message. Puis bouncer.with(ConversationPolicy).authorize('supprimerMessage', message) : message.userId (Ana) n'est pas Jo, donc refus et erreur E_AUTHORIZATION_FAILURE.
  10. Le handler, étape 0 : le message devient « Vous ne pouvez supprimer que vos propres messages. », avec le statut 403. Étape 2 : la requête vient d'un fetch, donc la réponse est 403 { message, errors: [{ message }] }.
  11. Dans le navigateur, lireErreur lit errors[0].message et kcNotifier.erreur(...) l'affiche. Le message d'Ana n'a pas bougé.

15. Ce qui a été remarqué

Ce qui est bien fait, à mettre en avant :

• Plusieurs couches de défense : le cookie httpOnly et sameSite, le jeton CSRF, la CSP avec nonce, HSTS, X-Frame-Options et nosniff.

• Le contrôle « connecté » posé une seule fois sur tout le groupe de routes, et les identifiants vérifiés par les matchers.

• Un seul format d'erreur pour le JavaScript, quel que soit l'endroit où l'erreur naît, et jamais de détail technique en production.

• Des limites d'essais stockées en base, qui résistent à un redémarrage.

• Des variables d'environnement validées au démarrage, avec les secrets masqués dans les logs.

1. (Corrigé le 08/11/2026) SESSION_DRIVER=memory fonctionne bien. config/session.ts ne déclare que cookie et database, mais defineConfig du paquet @adonisjs/session ajoute toujours un store memory à la liste. C'est lui que les tests utilisent (.env.test). Ce n'est donc pas un problème. Il ne faut simplement pas l'utiliser en production : les sessions seraient perdues à chaque redémarrage du serveur.

2. trustProxy: 'uniquelocal' dépend de l'hébergeur. Si le proxy de Render n'arrivait pas depuis une adresse du réseau interne, request.ip() renverrait l'IP du proxy pour tous les visiteurs. limiteEnvoiEmail deviendrait alors une limite de 5 e-mails par quart d'heure pour tout le site. À vérifier une fois en production, en affichant request.ip() dans un log.

3. styleSrc: 'unsafe-inline' affaiblit un peu la CSP pour les styles. C'est un compromis courant et peu risqué, car les scripts restent, eux, strictement protégés par le nonce.

4. /register (GET et POST) n'est pas dans le groupe guest, contrairement à /login. C'est sans danger, mais une personne connectée peut ouvrir la page d'inscription.

5. start/view.ts charge toute la collection d'icônes Lucide au démarrage (un gros fichier JSON), alors qu'aucune vue ne l'utilise. On pourrait retirer ce preload et les paquets edge-iconify et @iconify-json/lucide, ou au contraire s'en servir pour remplacer les SVG écrits à la main.
