conversations_controller.ts expliqué ligne par ligne

Kadea Chat · messagerie privée · fichier : app/controllers/conversations_controller.ts

Ce contrôleur gère la messagerie privée : afficher la page, ouvrir une conversation et en supprimer une de ta liste. On le suit de haut en bas, en expliquant chaque fonction importée au moment où elle sert.

Quatre méthodes publiques, une par route : elles reçoivent les requêtes, et les trois méthodes privées en bas préparent les données. Les petits outils réutilisés ailleurs sont rangés dans chat_service.ts.

Tout tourne autour de user_conversations : une ligne de cette table veut dire « cet utilisateur participe à cette conversation ». Le contrôleur l'appelle membership.

Supprimer une conversation ne supprime rien : le code enregistre seulement une date, removedAt, puis cache ce qui est plus ancien.

L'historique est paginé : à l'ouverture, seuls les 50 derniers messages sont chargés. Le bouton « Afficher les messages précédents » charge les 50 d'avant, et ainsi de suite.

Mis à jour le 06/11/2026 pour suivre les corrections P0, P1 et P2 : pagination, dossier app/services, alias #services/..., identifiants vérifiés dans les routes et lecture signalée à la suppression.

Les tables à connaître

Les relations, déclarées dans les modèles, permettent de passer d'une table à l'autre :

  • Depuis UserConversation : conversation mène à la conversation, et lastMessage au dernier message (app/models/user_conversation.ts).
  • Depuis Conversation : type donne 'Privee' ou 'Publique', users les utilisateurs et participants les lignes de user_conversations.
  • Depuis Message : attachments donne les fichiers joints, et statuses les états de lecture.

Les routes

Dans start/routes.ts, dans un groupe réservé aux utilisateurs connectés :

RequêteMéthode appeléeRôle

GET /conversations/:iddonneConversationOuvrir une conversation
GET /conversations/:id/messages?before=345donneMessagesPrecedentsCharger la page de messages d'avant

Chaque route avec :id porte maintenant .where('id', ID_NUMERIQUE), avec en haut du fichier const ID_NUMERIQUE = router.matchers.number(). La route ne correspond que si :id est un nombre. Pour /conversations/abc, aucune route ne correspond, donc 404, et le contrôleur n'est même pas appelé. Le matcher convertit aussi la valeur : params.id arrive déjà en nombre, et le Number(...) du contrôleur ne change plus rien.

2. donnePageMessages : la page de messagerie

async donnePageMessages({ auth, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const conversations = await this.donneListeConversations(user)

  return view.render('pages/message', { conversations, chat: null })
}
  • getUserOrFail() : récupère l'utilisateur connecté, ou lance une erreur s'il n'y en a pas.
  • this.donneListeConversations(user) : prépare la liste de gauche, expliquée en détail au point 6. this désigne le contrôleur.
  • chat: null : aucune conversation n'est ouverte, et la vue utilise @if(chat) pour afficher le panneau vide. C'est le @include('partials/chat-empty') de resources/views/partials/chat-panel.edge.

3. donneConversation : ouvrir une conversation

async donneConversation({ auth, params, request, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const chat = await this.donneDiscussion(user, Number(params.id))
  • params.id : le :id de l'adresse, par exemple 12 pour /conversations/12. Grâce au matcher de la route, c'est déjà un nombre. Number(...) reste comme sécurité, sans effet.
  • this.donneDiscussion : vérifie que tu fais partie de la conversation, puis prépare ses messages (point 7). Si tu n'en fais pas partie, l'erreur arrête tout ici.
  if (request.header('x-requested-with') === 'XMLHttpRequest') {
    return view.render('partials/chat-panel', { chat })
  }

Si la requête vient de fetch dans message.js (qui ajoute cet en-tête), la méthode renvoie seulement le panneau de discussion. Sinon (rechargement, lien direct), elle continue pour renvoyer la page entière.

  // La liste est chargée APRÈS donneDiscussion() : les messages sont déjà passés en "lu"
  const conversations = await this.donneListeConversations(user, chat.id)
  return view.render('pages/message', { conversations, chat })
}

La page entière contient la liste et le panneau. L'ordre compte, comme le dit le commentaire :

  1. donneDiscussion marque les messages comme lus.
  2. La liste est calculée ensuite, et cette conversation n'affiche donc plus de badge de non-lus.

Inversés, ces deux appels afficheraient un badge « 3 » à côté d'une conversation que tu es en train de lire.

chat.id est passé pour que la conversation ouverte reste visible dans la liste, même si elle était cachée (point 6).

Elle est appelée par le bouton « Afficher les messages précédents », en haut de la discussion. Elle renvoie la page de 50 messages juste avant le plus ancien déjà affiché.

  • olderMessagesValidator.validate(...) : on valide un objet donné, au lieu de request.validateUsing qui lit le corps de la requête. Le validateur, dans app/validators/message.ts :

  before: vine.number().withoutDecimals().positive(),

  const page = await this.chargeMessages(
    conversationId,
    otherMembership.userId,
    membership.removedAt,
    before

Elle charge la page, avec les mêmes règles qu'à l'ouverture : les messages cachés par removedAt restent cachés. La seule différence est le curseur before, au lieu de null. Voir le point 8.

5. supprimeConversation : retirer une conversation de ta liste

async supprimeConversation({ auth, params, response }: HttpContext) {
  const user = auth.getUserOrFail()
  const conversationId = Number(params.id)

Elle récupère l'utilisateur et l'identifiant de la conversation, comme au point 3.

  const membership = await chercheParticipationPrivee(user.id, conversationId).firstOrFail()

chercheParticipationPrivee vient de app/services/chat_service.ts :

export function chercheParticipationPrivee(userId, conversationId) {
  return UserConversation.query()
    .where('userId', userId)                    // ma participation...
    .where('conversationId', conversationId)    // ...à cette conversation...
    .whereHas('conversation', (conversationQuery) => {
      conversationQuery.whereHas('type', (typeQuery) => {
        typeQuery.where('type', PRIVATE_TYPE)   // ...et seulement si elle est privée
      })
    })
}
  • Elle ne fait que préparer : la fonction n'a pas d'async et renvoie une requête sans l'exécuter. Ça permet à chaque appelant d'ajouter ce qu'il veut, comme .preload(...) au point 7.
  • whereHas : veut dire « garde seulement les lignes qui ont une relation correspondant à ce critère ». Ici, deux niveaux sont imbriqués : la participation doit mener à une conversation, dont le type doit être 'Privee'.
  • .firstOrFail() : exécute la requête et prend la première ligne. S'il n'y en a aucune, il lance une erreur que AdonisJS transforme en 404.

C'est la vérification de sécurité de ce contrôleur : si tu essaies DELETE /conversations/99 sans en faire partie, aucune ligne n'existe pour toi, et la requête s'arrête sur une 404.

  membership.removedAt = DateTime.now()
  await membership.save()

Elle enregistre la date actuelle dans ta ligne de participation. Aucun message n'est supprimé, et la ligne de l'autre personne ne change pas, donc elle garde toute la conversation. Plus tard, le code ne te montrera que les messages postérieurs à cette date.

  await marqueConversationCommeLueEtPrevient(user.id, conversationId)

Elle passe tous tes messages non lus de cette conversation à « lu ». Sans ça, ton compteur de non-lus compterait encore des messages que tu ne peux plus voir. La fonction est la même qu'à l'ouverture d'une conversation (voir le point 7). Elle prévient aussi l'autre personne : ses coches passent au bleu en direct.

Ce qui a changé : avant, cette ligne appelait marqueConversationCommeLue, une version qui ne prévenait personne. Les messages étaient « lus » en base, mais l'autre ne voyait pas ses coches changer. Cette ancienne fonction a été supprimée de chat_service.ts : il n'y a plus qu'une seule façon de marquer comme lu.

  return response.ok({ message: 'La conversation a été supprimée.' })
}

Elle répond par un code 200 avec du JSON, et c'est le JavaScript de la page qui affiche le message.

6. donneListeConversations : la liste de gauche

C'est la méthode la plus longue. Elle se fait en quatre temps : charger les données, compter les non-lus, filtrer et préparer chaque ligne, puis trier.

private async donneListeConversations(user: User, openConversationId: number | null = null) {
  • private : elle n'est utilisable qu'à l'intérieur de cette classe, donc aucune route ne peut l'appeler directement.
  • openConversationId : l'identifiant de la conversation ouverte, s'il y en a une. = null le rend facultatif, et donnePageMessages ne le passe d'ailleurs pas.

Étape A : charger les participations

const memberships = await UserConversation.query()
  .where('userId', user.id)

Elle prend toutes tes participations.

  .whereHas('conversation', (conversationQuery) => {
    conversationQuery.whereHas('type', (typeQuery) => {
      typeQuery.where('type', PRIVATE_TYPE)
    })
  })

Elle ne garde que les conversations privées, avec le même filtre que dans chercheParticipationPrivee. Les groupes ont leur propre contrôleur.

  .preload('lastMessage', (messageQuery) => {
    messageQuery.preload('attachments')
  })

preload charge une relation en avance et l'attache à chaque résultat. Ici, il charge le dernier message de chaque conversation, et pour chacun de ces messages, ses fichiers joints. Ces fichiers servent à afficher « Image » dans l'aperçu.

  .preload('conversation', (conversationQuery) => {
    conversationQuery.preload('users', (usersQuery) => {
      usersQuery.whereNot('users.id', user.id)
    })
  })

Il charge aussi la conversation, avec ses utilisateurs sauf toi. Dans une conversation privée, il ne reste donc que l'autre personne. Le nom complet users.id est nécessaire, car cette requête joint plusieurs tables, et id seul serait ambigu.

Pourquoi preload ? Sans lui, il faudrait une requête par conversation pour son dernier message, puis une autre pour son interlocuteur. Avec 30 conversations, ça ferait plus de 60 requêtes, ce qu'on appelle le problème « N+1 ». Avec preload, Lucid fait une requête par relation, quel que soit le nombre de conversations.

memberships ressemble alors à :

donneNombreMessagesNonLus vient de app/services/chat_service.ts :

7. donneDiscussion : préparer la conversation ouverte

private async donneDiscussion(user: User, conversationId: number) {
  const membership = await chercheParticipationPrivee(user.id, conversationId)
    .preload('conversation', (conversationQuery) => {
      conversationQuery.preload('users', (usersQuery) => {
        usersQuery.whereNot('users.id', user.id)
      })
    })
    .firstOrFail()

Elle reprend chercheParticipationPrivee, en y ajoutant un preload de l'interlocuteur. C'est possible parce que cette fonction renvoie une requête pas encore exécutée. firstOrFail() garantit une 404 si tu ne fais pas partie de la conversation : c'est ce qui empêche de lire celle d'autres personnes en changeant l'identifiant dans l'adresse.

  const otherUser = membership.conversation.users[0]
  if (!otherUser) {
    throw new Error('Interlocuteur introuvable pour cette conversation.')
  }

8. chargeMessages et chargePageMessages : la pagination

private chargeMessages(
  conversationId: number,
  otherUserId: User['id'],
  removedAt: DateTime | null,
  before: number | null
) {
  return chargePageMessages({
    conversationId,
    before,
    visibleAfter: removedAt,
    prepare: (query) => {
      query.preload('attachments').preload('statuses', (statusQuery) => {
        statusQuery.where('userId', otherUserId) // pour les coches de mes messages
      })
    },
  })
}

Elle ne contient que ce qui est propre aux conversations privées : les fichiers joints et les statuts de l'autre personne. Le reste est fait par chargePageMessages, qui sert aussi aux groupes.

  • Pas de async : elle renvoie directement la promesse de chargePageMessages. Les appelants font le await.
  • prepare : une fonction passée en paramètre. chargePageMessages l'appelle avec sa requête en construction, et chaque contrôleur y ajoute ses preload. En groupe, par exemple, on charge en plus l'auteur de chaque message.

chargePageMessages, dans app/services/chat_service.ts :

export async function chargePageMessages(options: {
  conversationId: number
  before: number | null
  visibleAfter: DateTime | null
  prepare: (query: ModelQueryBuilderContract<typeof Message>) => void
}) {
  const query = Message.query()
    .where('conversationId', options.conversationId)
    .orderBy('id', 'desc')
    .limit(MESSAGES_PER_PAGE + 1)

  if (options.before !== null) {
    query.where('id', '<', options.before)
  }
  if (options.visibleAfter !== null) {
    query.where('createdAt', '>', options.visibleAfter.toJSDate())
  }
  options.prepare(query)

  const rows = await query
  const hasMore = rows.length > MESSAGES_PER_PAGE
  const messages = rows.slice(0, MESSAGES_PER_PAGE).reverse()

  return { messages, hasMore, oldestId: messages[0]?.id ?? null }
}
  • Un seul paramètre options : un objet avec des noms. À l'appel, { conversationId, before, visibleAfter, prepare } se lit mieux que quatre valeurs dans un ordre à retenir.
  • ModelQueryBuilderContract<typeof Message> : le type d'une requête Lucid sur le modèle Message. TypeScript sait ainsi que query.preload('attachments') est valide.
  • orderBy('id', 'desc') : du plus récent au plus ancien. Les identifiants augmentent avec le temps, donc un identifiant plus grand veut dire un message plus récent.
  • limit(MESSAGES_PER_PAGE + 1) : on demande 51 messages pour une page de 50. Le 51ᵉ n'est pas affiché : il sert seulement à savoir s'il en reste d'autres. Ça évite une seconde requête count.
  • where('id', '<', before) : la pagination par curseur. « Donne-moi ceux qui sont avant le message 345 ».
  • visibleAfter : la règle de removedAt, appliquée à chaque page. Les anciens messages restent cachés, même avec le bouton.
  • options.prepare(query) : ajoute les preload propres à l'appelant.
  • hasMore : vrai si la base a renvoyé plus de 50 lignes.
  • slice(0, 50).reverse() : on garde 50 messages, puis on les remet du plus ancien au plus récent, l'ordre de lecture.
  • oldestId : l'identifiant du premier message après le reverse, donc le plus ancien de la page. C'est le prochain curseur. ?. et ?? null gèrent une page vide.

Pourquoi un curseur plutôt qu'un numéro de page ? Avec « page 2 = messages 51 à 100 », il y a un problème si Ana envoie 3 messages pendant que tu lis. Tout se décale de 3, et la page 2 répéterait 3 messages déjà affichés. Avec « avant le message 345 », l'arrivée de nouveaux messages ne change rien : 345 reste 345.

Corrigé depuis la première version de ce document :

• La suppression prévient maintenant l'auteur : supprimeConversation utilise marqueConversationCommeLueEtPrevient, et les coches de l'autre passent au bleu en direct.
