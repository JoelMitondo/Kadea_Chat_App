Profil et paramètres expliqués ligne par ligne

profile_controller.ts · settings_controller.ts · validators/profile.ts et account.ts · pages/profile.edge et settings.edge · profile.js · settings.js · theme.js

Deux pages réservées à la personne connectée : le profil (voir et modifier ses informations et sa photo, avec quelques statistiques) et les paramètres (changer son mot de passe, gérer les personnes bloquées, supprimer son compte). On y ajoute le bouton clair / sombre, présent sur toutes les pages.

Les deux règles qui reviennent :

• Les actions sensibles redemandent le mot de passe actuel (changer le mot de passe, supprimer le compte). Quelqu'un qui trouverait la session ouverte sur un ordinateur ne peut pas prendre le contrôle du compte.

• Pour la photo, toujours le même ordre : envoyer la nouvelle, enregistrer en base, puis seulement supprimer l'ancienne. À aucun moment le profil ne se retrouve sans photo valide.

2. donneProfil : afficher le profil

Les imports

import type { HttpContext } from '@adonisjs/core/http'
import { type DateTime } from 'luxon'
import type User from '#models/user'
import Message from '#models/message'
import UserConversation from '#models/user_conversation'
import { updateProfileValidator } from '#validators/profile'
import { supprimeImageParLien, envoiePhotoProfil } from '#services/cloudinary_service'
import { AGE_MINIMUM, GROUP_TYPE, PRIVATE_TYPE, donneInitiales, estMajeur } from '#services/chat_service'
  • import { type DateTime } : DateTime ne sert qu'à décrire un paramètre. Le mot type placé dans les accolades marque cet import comme « type seulement ».
  • Message et UserConversation servent aux statistiques.
  • Les deux fonctions de Cloudinary envoient la nouvelle photo et suppriment l'ancienne.
  • estMajeur et AGE_MINIMUM viennent de chat_service.ts. Avant, le contrôleur avait sa propre copie de estMajeur. Elle a été regroupée avec celle de l'inscription (corrections P2).

La méthode

async donneProfil({ auth, view }: HttpContext) {
  const user = auth.getUserOrFail()

  const privateChats = await this.compteConversations(user.id, PRIVATE_TYPE)
  const groups = await this.compteConversations(user.id, GROUP_TYPE)
  const messages = await this.compteMessages(user.id)

  return view.render('pages/profile', {
    profile: {
      fullName: user.fullName,
      initials: donneInitiales(user.fullName),
      bio: user.bio ?? '',
      avatarUrl: user.avatarUrl,
      phoneNumber: user.phoneNumber ?? '',
      birthDateLabel: this.formateDate(user.birthDate),
      birthDateValue: user.birthDate ? user.birthDate.toISODate() : '',
      email: user.email,
      createdAt: this.formateDate(user.createdAt),
    },
    stats: { privateChats, groups, messages },
  })
}
  • Trois statistiques : le nombre de conversations privées, de groupes et de messages. Elles sont détaillées au point 3.
  • bio: user.bio ?? '' et phoneNumber: user.phoneNumber ?? '' : le commentaire du code raconte un vrai bug corrigé.
    1. Edge écrit null sous la forme du texte "null" dans value="{{ profile.phoneNumber }}".
    2. Un téléphone vide devenait donc le texte « null » dans le champ du formulaire.
    3. À l'enregistrement, « null » ne respectait pas le format d'un numéro, et le profil ne pouvait plus être enregistré du tout.
  • Deux versions de la date de naissance :
    • birthDateLabel, lisible (« 12/04/1998 »), pour l'affichage ;
    • birthDateValue, au format AAAA-MM-JJ (toISODate()), le seul format qu'accepte un champ <input type="date">.
  • On n'envoie à la vue que ce qu'elle affiche, jamais l'objet user complet avec son mot de passe haché.
private formateDate(date: DateTime | null | undefined): string {
  return date ? date.toFormat('dd/MM/yyyy') : 'Non renseignée'
}

Une date lisible, ou « Non renseignée » si elle est vide. Le type DateTime | null | undefined accepte les trois cas.

3. Les statistiques

compteConversations

private async compteConversations(userId: User['id'], typeName: string): Promise<number> {
  const result = await UserConversation.query()
    .where('userId', userId)
    .whereHas('conversation', (conversationQuery) => {
      conversationQuery.whereHas('type', (typeQuery) => {
        typeQuery.where('type', typeName)
      })
    })
    .count('* as total')
    .first()

  return Number(result?.$extras.total ?? 0)
}
  • On compte les participations de l'utilisateur dont la conversation est du type demandé ('Privee' ou 'Publique'). C'est le même double whereHas que dans chercheParticipation.
  • count('* as total') fait compter la base (SELECT COUNT(*)) au lieu de charger toutes les lignes pour les compter en JavaScript.
  • .first() : un COUNT renvoie une seule ligne.
  • $extras.total : une colonne calculée, qui n'existe pas dans le modèle, est rangée par Lucid dans $extras.
  • Number(... ?? 0) : PostgreSQL renvoie le compte en texte ("3"). ?? 0 protège si aucune ligne n'est revenue.

compteMessages

private async compteMessages(userId: User['id']): Promise<number> {
  const myConversations = UserConversation.query()
    .select('conversation_id')
    .where('user_id', userId)

  const result = await Message.query()
    .whereIn('conversation_id', myConversations)
    .where('is_deleted', false)
    .count('* as total')
    .first()

  return Number(result?.$extras.total ?? 0)
}
  • « Messages envoyés et reçus » : tous les messages des conversations dont l'utilisateur fait partie.
  • myConversations n'a pas de await : c'est une requête non exécutée, glissée dans whereIn comme sous-requête. En SQL : WHERE conversation_id IN (SELECT conversation_id FROM user_conversations WHERE user_id = ...). Tout se fait en une seule requête.
  • is_deleted = false : un message supprimé n'est plus compté.

4. modifieProfil : enregistrer les modifications et la photo

Le validateur

export const updateProfileValidator = vine.create({
  full_name: vine.string().trim().minLength(2).maxLength(100),
  bio: vine.string().trim().maxLength(500).optional(),
  phone_number: vine.string().trim().regex(/^\+?[0-9\s-]{8,20}$/).optional(),
  birth_date: vine.date().beforeOrEqual('today'),
  avatar: vine.file({ size: '5mb', extnames: ['jpg', 'jpeg', 'png', 'webp'] }).optional(),
})
  • phone_number doit respecter la regex /^\+?[0-9\s-]{8,20}$/ : un + facultatif au début (\+?), puis 8 à 20 caractères parmi les chiffres, les espaces et les tirets. Par exemple, +243 812 345 678 est accepté, abc est refusé.
  • beforeOrEqual('today') : une date de naissance dans le futur est refusée par le validateur. L'âge minimum, lui, est vérifié juste après dans le contrôleur.
  • vine.file({ size: '5mb', extnames: [...] }) : la photo fait 5 Mo au plus, en JPG, PNG ou WebP. AdonisJS vérifie l'extension et le vrai type du fichier, lu dans ses premiers octets. Renommer un .exe en .jpg ne suffit donc pas.
  • .optional() : la bio, le téléphone et la photo peuvent manquer. Pour ces champs, un champ vide devient null (réglage convertEmptyStringsToNull du bodyparser), puis undefined après validation.

Le début : validation et âge

async modifieProfil(ctx: HttpContext) {
  const { auth, request, response, session, logger } = ctx
  const user = auth.getUserOrFail()
  const payload = await request.validateUsing(updateProfileValidator)

  if (!estMajeur(payload.birth_date)) {
    return this.refuseChamp(ctx, 'birth_date', `Vous devez avoir au moins ${AGE_MINIMUM} ans.`)
  }
  • modifieProfil(ctx: HttpContext) reçoit le contexte entier, puis le découpe. C'est nécessaire, car ctx est passé tel quel à refuseChamp.
  • logger est le logger de la requête : chaque ligne écrite porte l'identifiant de la requête.
  • On ne peut pas devenir mineur en modifiant son profil : la règle des 18 ans est revérifiée ici, pas seulement à l'inscription.

Étape 1 : envoyer la nouvelle photo

  const oldAvatarUrl = user.avatarUrl
  let newAvatarUrl: string | null = null

  const avatarTmpPath = payload.avatar?.tmpPath
  if (avatarTmpPath) {
    try {
      newAvatarUrl = await envoiePhotoProfil(avatarTmpPath)
    } catch (error) {
      logger.error({ err: error }, "Échec de l'envoi de la photo vers Cloudinary")
      return this.refuseChamp(ctx, 'avatar', "Impossible d'envoyer la photo pour le moment. Réessayez dans un instant.")
    }
  }
  • On garde l'ancien lien (oldAvatarUrl), car on en aura besoin à la fin.
  • payload.avatar?.tmpPath : le chemin du fichier temporaire créé par le bodyparser. Le ?. renvoie undefined s'il n'y a pas de nouvelle photo.
  • envoiePhotoProfil l'envoie vers Cloudinary, en carré de 512 × 512 (voir le fichier sur les services).
  • Si l'envoi échoue, comme le dit le commentaire : rien n'a changé, l'ancienne photo est toujours là. On répond par une erreur sous le champ « photo ».

Étape 2 : enregistrer en base

  try {
    user.merge({
      fullName: payload.full_name,
      bio: payload.bio ?? null,
      phoneNumber: payload.phone_number ?? null,
      birthDate: payload.birth_date,
      avatarUrl: newAvatarUrl ?? oldAvatarUrl,
    })
    await user.save()
  } catch (error) {
    await supprimeImageParLien(newAvatarUrl)
    throw error
  }
  • merge({...}) copie plusieurs valeurs dans le modèle d'un coup, comme une série de user.x = .... Rien n'est encore enregistré : c'est save() qui écrit en base, et seulement les colonnes qui ont changé.
  • payload.bio ?? null : un champ facultatif laissé vide arrive en undefined. ?? null le transforme en null, ce qui vide la colonne. Avec undefined, Lucid laisserait l'ancienne valeur en place, et effacer sa bio serait impossible.
  • newAvatarUrl ?? oldAvatarUrl : la nouvelle photo s'il y en a une, sinon on garde l'ancienne.
  • Si la base refuse, la nouvelle image ne sert plus à rien : on la supprime de Cloudinary, puis throw error relance l'erreur pour que le handler réponde normalement. supprimeImageParLien(null) ne fait rien, ce qui couvre le cas sans nouvelle photo.

Étape 3 : supprimer l'ancienne photo, puis répondre

  if (newAvatarUrl) {
    await supprimeImageParLien(oldAvatarUrl)
  }

  if (request.accepts(['html', 'json']) === 'json') {
    return response.ok({ message: 'Votre profil a été mis à jour.' })
  }
  session.flash('success', 'Votre profil a été mis à jour.')
  return response.redirect().toRoute('profile')
}
  • Seulement maintenant, tout étant enregistré, l'ancienne photo est supprimée. Si cette suppression échouait, il resterait juste un fichier inutile sur Cloudinary. Le profil, lui, serait correct.
  • La réponse : le formulaire porte data-ajax et data-redirect="/profile". Le script affiche « Votre profil a été mis à jour. » puis recharge la page. Le commentaire explique pourquoi on ne met pas de message flash dans ce cas : il s'afficherait une deuxième fois après le rechargement. Le flash ne sert que si le formulaire est envoyé sans JavaScript.

Pourquoi cet ordre précis ?

Si ça échoue à…Résultat
L'envoi de la nouvelle photoRien n'a changé : ancienne photo, anciennes infos
L'enregistrement en baseNouvelle photo supprimée de Cloudinary, ancienne photo et anciennes infos gardées
La suppression de l'ancienne photoProfil à jour, un fichier oublié sur Cloudinary (sans effet visible)

Dans l'ordre inverse (supprimer l'ancienne d'abord), un échec au milieu laisserait un profil avec une photo cassée.

5. refuseChamp : une erreur sous le bon champ

private refuseChamp(ctx: HttpContext, field: string, message: string) {
  if (ctx.request.accepts(['html', 'json']) === 'json') {
    return ctx.response.unprocessableEntity({ errors: [{ field, message }] })
  }
  ctx.session.flash('error', message)
  return ctx.response.redirect().back()
}
  • Pour le script : une 422 au format { errors: [{ field, message }] }, le même que les erreurs de validation. notifications.js place le message sous le champ indiqué (birth_date ou avatar).
  • Pour un formulaire classique : un message flash, et retour à la page précédente.
  • Pourquoi on passe ctx entier ? La fonction a besoin de trois morceaux : request (pour savoir qui demande), response et session.
  • Le bug corrigé, raconté dans le commentaire : avant, une redirection était renvoyée même au script. fetch la suivait, recevait la page profil avec le code 200, et affichait « Votre profil a été mis à jour » alors que rien n'avait été enregistré. C'est le même piège que celui que règle handler.ts pour toutes les erreurs (voir le fichier sur le socle).

6. La page profil et profile.js

Ce qu'affiche profile.edge

  • L'en-tête : les initiales, avec la photo par-dessus. data-remove-on-error retire la photo si elle ne se charge plus, et les initiales réapparaissent. C'est le petit script de head-script.edge, car les attributs onerror sont interdits par la CSP.
  • Trois cartes de statistiques (components/stat-card), puis les informations détaillées (components/info-row) : téléphone (ou « Non renseigné »), date de naissance, e-mail, date d'inscription.
  • Un bouton « Modifier » (data-modal-open="profile-modal") qui ouvre la fenêtre de modification.

Le formulaire de la fenêtre

<dialog id="profile-modal">
  <form action="{{ route('profile.update') }}" method="POST"
        enctype="multipart/form-data"
        data-ajax data-no-reset
        data-success="Votre profil a été mis à jour."
        data-loading-text="Enregistrement…"
        data-redirect="/profile">
    <input name="full_name" value="{{ profile.fullName }}" required>
    <textarea name="bio" maxlength="500">{{ profile.bio }}</textarea>
    <input name="phone_number" type="tel" value="{{ profile.phoneNumber }}">
    <input name="birth_date" type="date" value="{{ profile.birthDateValue }}" required>
    <img id="avatar-preview" src="{{ profile.avatarUrl }}" data-current="{{ profile.avatarUrl }}" data-hide-on-error>
    <input id="avatar" name="avatar" type="file" ...>
  </form>
</dialog>
  • <dialog> est une fenêtre modale intégrée au navigateur. showModal() l'ouvre par-dessus la page, avec un fond sombre, et bloque le reste de la page. Échap la ferme.
  • enctype="multipart/form-data" est indispensable pour envoyer un fichier. Sans lui, seul le nom du fichier partirait. notifications.js utilise new FormData(formulaire), qui respecte ce format.
  • data-no-reset : après le succès, le script ne vide pas le formulaire. La page va de toute façon être rechargée (data-redirect).
  • Les champs sont pré-remplis avec les valeurs actuelles. D'où l'importance du ?? '' vu au point 2.
  • data-current garde l'adresse de la photo actuelle, pour pouvoir revenir à l'aperçu d'origine.

profile.js

Tout le code est dans un if : si la page n'a pas de fenêtre de profil, il ne fait rien. Les mêmes limites que le validateur sont reprises ici : 5 Mo, et trois types d'image.

  function ouvrirModale() {
    modale.showModal()
  }

  function restaurerApercu() {
    let photoActuelle = apercu.dataset.current
    if (photoActuelle) {
      apercu.src = photoActuelle
      apercu.classList.remove('hidden')
    } else {
      apercu.removeAttribute('src')
      apercu.classList.add('hidden')
    }
  }

  function fermerModale() {
    formulaire.reset()
    restaurerApercu()
    modale.close()
  }
  • restaurerApercu remet l'aperçu sur la photo enregistrée (dataset.current lit l'attribut data-current), ou le cache s'il n'y en a pas.
  • fermerModale annule les modifications non enregistrées. formulaire.reset() remet chaque champ à la valeur qu'il avait au chargement de la page. Rouvrir la fenêtre montre donc les vraies valeurs, pas un brouillon abandonné.
  boutonsOuvrir.forEach(function (bouton) { bouton.addEventListener('click', ouvrirModale) })
  boutonsFermer.forEach(function (bouton) { bouton.addEventListener('click', fermerModale) })

  modale.addEventListener('click', function (evenement) {
    if (evenement.target === modale) {
      fermerModale()
    }
  })

Le clic sur le fond sombre : le fond d'un <dialog> fait partie de l'élément <dialog> lui-même. Un clic sur le fond a donc pour cible (evenement.target) le dialog. Un clic dans la carte a pour cible un de ses enfants (un champ, un texte), et la fenêtre reste ouverte.

  champPhoto.addEventListener('change', function () {
    let fichier = champPhoto.files[0]
    if (fichier === undefined) {
      restaurerApercu()
      return
    }
    if (TYPES_ACCEPTES.indexOf(fichier.type) === -1) {
      kcNotifier.erreur('Format non accepté. Choisissez une image JPG, PNG ou WebP.')
      champPhoto.value = ''
      restaurerApercu()
      return
    }
    if (fichier.size > TAILLE_MAX) {
      kcNotifier.erreur("L'image est trop lourde : 5 Mo maximum.")
      champPhoto.value = ''
      restaurerApercu()
      return
    }
    apercu.src = URL.createObjectURL(fichier)
    apercu.classList.remove('hidden')
  })
}
  • change se déclenche quand on choisit un fichier. files[0] est le fichier choisi, ou undefined si on a annulé.
  • Vérifications immédiates : le type (indexOf(...) === -1 veut dire « absent de la liste ») et la taille. En cas de problème, un message s'affiche, le champ est vidé (value = '') et l'aperçu revient à la photo actuelle. On évite ainsi d'envoyer 20 Mo pour se faire refuser par le serveur.
  • URL.createObjectURL(fichier) crée une adresse temporaire blob:… qui pointe vers le fichier sur l'ordinateur. L'aperçu s'affiche instantanément, sans rien envoyer. C'est pour ça que la CSP autorise blob: dans imgSrc.
  • Ces vérifications aident, mais ne protègent pas : le serveur revérifie tout avec updateProfileValidator.

7. donnePageParametres : la page Paramètres

Les imports

import BlockedUser from '#models/blocked_user'

La méthode

async donnePageParametres({ auth, view }: HttpContext) {
  const user = auth.getUserOrFail()

  const blockedRows = await BlockedUser.query()
    .where('blockerId', user.id)
    .preload('blocked')
    .orderBy('id', 'desc')

  const blockedUsers = blockedRows.map((row) => ({
    id: row.blocked.id,
    fullName: row.blocked.fullName,
    initials: donneInitiales(row.blocked.fullName),
    avatarUrl: row.blocked.avatarUrl,
  }))

  return view.render('pages/settings', { blockedUsers })
}
  • Les personnes que j'ai bloquées : les lignes de blocked_users où je suis celui qui bloque (blockerId).
  • preload('blocked') charge, pour chaque ligne, l'utilisateur bloqué. C'est une relation belongsTo du modèle BlockedUser (foreignKey: 'blockedId'). On a besoin de son nom et de sa photo.
  • orderBy('id', 'desc') : le blocage le plus récent en premier.
  • Le map ne garde que ce que la vue affiche.

8. Changer son mot de passe

Le validateur

export const changePasswordValidator = vine.create({
  current_password: vine.string(),
  password: vine.string().minLength(8).maxLength(50).confirmed().notSameAs('current_password'),
})
  • confirmed() : un champ password_confirmation identique est exigé.
  • notSameAs('current_password') : le nouveau mot de passe doit être différent de l'actuel. « Changer » son mot de passe pour le même n'aurait aucun sens.
  • Le validateur a ses propres messages en français (« Le nouveau mot de passe doit être différent de l'actuel. »…).

modifieMotDePasse

async modifieMotDePasse({ auth, request, response, session }: HttpContext) {
  const user = auth.getUserOrFail()
  const { current_password: currentPassword, password } = await request.validateUsing(changePasswordValidator)

  const isValid = await hash.verify(user.password, currentPassword)
  if (!isValid) {
    return response.unprocessableEntity({
      errors: [{ field: 'current_password', message: 'Mot de passe actuel incorrect.' }],
    })
  }

  user.password = password
  await user.save()

  const message = 'Votre mot de passe a été modifié.'
  if (request.accepts(['html', 'json']) === 'json') {
    return response.ok({ message })
  }
  session.flash('success', message)
  return response.redirect().toRoute('settings')
}

Le commentaire au-dessus de la méthode décrit les 3 étapes :

  1. La forme, vérifiée par le validateur.
  2. Le mot de passe actuel : hash.verify(hashEnregistré, motDePasseTapé). user.password contient le hash, jamais le mot de passe en clair. En cas d'erreur, le message s'affiche sous le champ « mot de passe actuel ». Quelqu'un qui trouverait la session ouverte ne peut pas changer le mot de passe sans le connaître.
  3. L'enregistrement : withAuthFinder hache automatiquement le nouveau mot de passe avant le save().

La personne reste connectée : sa session n'a pas changé.

demarreChangementMotDePasse : « j'ai oublié mon mot de passe actuel »

async demarreChangementMotDePasse({ auth, response, session }: HttpContext) {
  await auth.use('web').logout()

  session.flash('success', 'Vous avez été déconnecté. Saisissez votre adresse e-mail pour recevoir le lien de réinitialisation.')

  return response.redirect().toRoute('forgotPassword.get')
}
  • Le cas : on veut changer son mot de passe, mais on ne se souvient plus de l'actuel. Le formulaire du changement exige pourtant l'actuel.
  • La solution : déconnecter la personne et l'envoyer sur « Mot de passe oublié », qui fait déjà tout le reste (lien par e-mail, nouveau mot de passe). On réutilise un parcours existant au lieu d'en écrire un deuxième.
  • Pourquoi déconnecter d'abord ? La page « Mot de passe oublié » est réservée aux visiteurs non connectés (middleware guest). Une personne encore connectée serait renvoyée vers l'accueil.
  • Ce n'est pas une faille : sans accès à la boîte e-mail, la déconnexion ne mène à rien. C'est l'e-mail qui prouve l'identité.

async supprimeCompte({ auth, request, response }: HttpContext) {
  const user = auth.getUserOrFail()
  const { password } = await request.validateUsing(deleteAccountValidator)

  try {
    await User.verifyCredentials(user.email, password)
  } catch {
    return response.unprocessableEntity({
      errors: [{ field: 'password', message: 'Mot de passe incorrect.' }],
    })
  }

  await supprimeCompteUtilisateur(user)

  await auth.use('web').logout()

  return response.ok({ message: 'Votre compte a été supprimé définitivement.' })
}
  1. Vérifier que c'est bien lui : verifyCredentials lance une erreur si le mot de passe est faux. On l'attrape (try / catch, sans variable puisqu'on n'en a pas besoin) pour afficher « Mot de passe incorrect. » sous le champ.
  2. Tout supprimer avec supprimeCompteUtilisateur, dans une transaction : conversations privées, messages de groupe, transmission du rôle d'administrateur, blocages, fichiers sur Cloudinary, notifications aux autres. Tout est expliqué dans le fichier sur les services.
  3. Déconnecter : le compte n'existe plus, la session ne doit plus pointer vers lui.

Le formulaire porte data-redirect="/" : après le message, le navigateur part sur l'accueil.

10. La page Paramètres et settings.js

Ce qu'affiche settings.edge

  • Mot de passe : un bouton qui ouvre la fenêtre password-dialog.
  • Utilisateurs bloqués : « aucun » si blockedUsers.length === 0, sinon une ligne par personne, avec un petit formulaire « Débloquer » (POST vers route('users.unblock', { id })).
  • Supprimer mon compte : un bouton qui ouvre la fenêtre delete-dialog.

La fenêtre du mot de passe contient deux formulaires :

  • le principal (data-ajax, data-redirect="/settings"), avec current_password, password et password_confirmation ;
  • en dessous, un petit formulaire classique « J'ai oublié mon mot de passe actuel », vers settings.password.forgot.

La fenêtre de suppression redemande le mot de passe.

settings.js

function brancherFenetre(idBouton, idFenetre) {
  let bouton = document.getElementById(idBouton)
  let fenetre = document.getElementById(idFenetre)

  if (bouton === null || fenetre === null) { return }

  bouton.addEventListener('click', function () {
    fenetre.showModal()
  })

  fenetre.querySelectorAll('[data-modal-close]').forEach(function (boutonFermer) {
    boutonFermer.addEventListener('click', function () {
      fenetre.close()
    })
  })

  fenetre.addEventListener('click', function (evenement) {
    if (evenement.target === fenetre) {
      fenetre.close()
    }
  })

  fenetre.addEventListener('close', function () {
    fenetre.querySelectorAll('form').forEach(function (formulaire) { formulaire.reset() })
  })
}

brancherFenetre('open-password-dialog', 'password-dialog')
brancherFenetre('open-delete-dialog', 'delete-dialog')
  • Une seule fonction pour deux fenêtres : elle relie un bouton à une fenêtre, et on l'appelle deux fois. Sans elle, il faudrait écrire deux fois le même code.
  • Ce qui ouvre la fenêtre : le bouton. Ce qui la ferme : « Annuler » / « Non » (data-modal-close), ou un clic sur le fond sombre (même technique que dans profile.js).
  • L'événement close se déclenche quelle que soit la façon de fermer, touche Échap comprise. On y vide les formulaires : un mot de passe tapé ne reste pas dans le champ, visible par la prochaine personne qui ouvrirait la fenêtre.

11. theme.js : le mode clair / sombre

let bouton = document.getElementById('theme-toggle')

if (bouton !== null) {
  bouton.addEventListener('click', function () {
    let html = document.documentElement
    let nouveauTheme = html.dataset.theme === 'dark' ? 'light' : 'dark'

    html.dataset.theme = nouveauTheme
    try { localStorage.setItem('theme', nouveauTheme) } catch (erreur) {}
  })
}
  • Le bouton #theme-toggle est présent dans les trois layouts (app, auth, landing). theme.js est importé par compiles/animate.js, chargé partout.
  • document.documentElement est la balise <html>. On y écrit data-theme="dark" ou "light", et le CSS change les couleurs selon cet attribut.
  • localStorage garde le choix dans le navigateur, d'une visite à l'autre. Le try { } catch { } vide évite une erreur si le stockage est bloqué (navigation privée, réglages stricts). Le thème change quand même, il n'est simplement pas mémorisé.
  • L'autre moitié est dans partials/head-script.edge : au chargement de chaque page, avant l'affichage, un petit script lit localStorage. Faute de choix enregistré, il suit le réglage du système (prefers-color-scheme). Il est placé dans <head> pour éviter un « flash » blanc avant le passage au sombre. Il porte le nonce de la CSP.

Ana change sa photo

  → POST /profile (multipart, data-ajax)
  → updateProfileValidator → estMajeur ?
  → 1. nouvelle photo → Cloudinary (512 × 512)       échec ? erreur sous « photo », rien n'a changé
  → 2. user.merge + save                             échec ? nouvelle photo supprimée
  → 3. ancienne photo supprimée de Cloudinary
  → 200 → notification, puis rechargement de /profile

12. Ce qui a été remarqué

Ce qui est bien fait, à mettre en avant :

• L'ordre envoi → base → suppression de l'ancienne photo, avec un nettoyage si la base refuse.

• Le mot de passe actuel est redemandé pour les actions sensibles, avec une limite d'essais par compte.

• Les erreurs reviennent toujours sous le bon champ (refuseChamp), et deux bugs réels sont corrigés et expliqués dans les commentaires (le texte « null », la fausse réussite).

• Les fenêtres se vident à la fermeture et ne gardent jamais un mot de passe tapé.

1. Le format du téléphone n'est pas le même partout. Le profil exige /^\+?[0-9\s-]{8,20}$/, mais la création de compte accepte n'importe quel texte (confirmationCompteValidator n'a pas de regex). Quelqu'un qui a tapé « 0812 345 » (7 chiffres) ou « néant » à l'inscription ne pourra plus enregistrer aucune modification de son profil tant qu'il n'aura pas corrigé son téléphone. Il suffit de mettre la même regex dans les deux validateurs, par exemple dans une petite fonction partagée.

2. Le nombre de messages ne tient pas compte de removedAt. Après avoir supprimé une conversation de sa liste, ses anciens messages ne s'affichent plus, mais compteMessages les compte encore. Ce point était déjà signalé dans le fichier sur les conversations.

3. La date d'inscription n'est pas convertie à l'heure de Kinshasa. Le formateDate privé du contrôleur n'appelle pas setZone(APP_TIMEZONE), contrairement à formateDate de chat_service.ts. Un compte créé entre 23 h et minuit, heure de Kinshasa, affiche la date du lendemain. On peut utiliser la fonction de chat_service.ts pour createdAt et garder la version actuelle pour la date de naissance, qui n'a pas d'heure.

4. Changer son mot de passe ne déconnecte pas les autres appareils (même remarque que pour le mot de passe oublié).

5. Deux façons de vérifier le mot de passe actuel : hash.verify dans modifieMotDePasse, verifyCredentials dans supprimeCompte. Les deux sont justes, mais un seul style serait plus lisible.

6. Détail sans gravité dans profile.js : chaque aperçu crée une adresse blob: avec URL.createObjectURL, sans jamais la libérer avec URL.revokeObjectURL. La mémoire n'est rendue qu'au rechargement de la page, ce qui arrive juste après l'enregistrement. L'impact est nul en pratique.
