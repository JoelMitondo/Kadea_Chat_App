Les tests de Kadea Chat expliqués pas à pas

Pour quelqu'un qui n'a jamais écrit de test · package.json, adonisrc.ts, .env.test, bin/test.ts, tests/bootstrap.ts, tests/helpers.ts, tests/functional/*.spec.ts

Ce document part de zéro. Il explique d'abord ce qu'est un test et pourquoi on en écrit. Il décrit ensuite tout ce qui se passe quand on tape npm test, fichier par fichier. Enfin, il reprend chacun des 36 tests du projet en disant ce qu'il vérifie, comment, et pourquoi c'est important.

L'idée à retenir : un test automatique est un petit programme qui utilise ton application à ta place et qui vérifie que le résultat est celui attendu. Au lieu d'ouvrir le navigateur, de te connecter avec deux comptes et d'essayer d'écrire dans la conversation de quelqu'un d'autre, tu lances une commande. En quelques secondes, les 36 vérifications sont refaites, toujours de la même façon.

1. C'est quoi un test, et pourquoi en écrire ?

Une comparaison avec la vie courante

Pense au contrôle technique d'une voiture. Le contrôleur ne la démonte pas : il l'utilise (freine, allume les phares, klaxonne) et compare à ce qui est attendu (« la voiture doit s'arrêter en moins de X mètres »). S'il y a un écart, il le note.

Un test automatique fait la même chose avec ton site :

  1. il prépare une situation (crée Alice, Bob et une conversation entre eux) ;
  2. il agit (un intrus essaie d'écrire dans cette conversation) ;
  3. il vérifie (le serveur doit répondre « 404 » et aucun message ne doit être enregistré).

Si la vérification échoue, le test est « rouge » et affiche ce qui ne va pas. Sinon il est « vert ».

Pourquoi c'est précieux (et à dire au jury)

  • Prouver que les règles de sécurité marchent : « un non-membre ne peut ni lire ni écrire », ce n'est pas une promesse, c'est vérifié à chaque lancement.
  • Éviter les régressions : une régression, c'est casser sans le vouloir quelque chose qui marchait. Pendant les corrections P0, P1, P2, les tests ont permis de modifier le code sans peur.
  • Documenter : le nom de chaque test est une phrase en français qui décrit une règle du site. La liste des tests est une liste des règles.
  • Garder la trace des bugs corrigés : plusieurs tests sont nés d'un bug (« un champ vide ne s'affiche pas comme le texte null », « la mention NMS Tech a disparu du pied de page »). Le test empêche le bug de revenir.

3. Les trois familles de tests (et celle utilisée ici)

FamilleCe qu'elle testeComparaisonDans le projet
Unitaire (unit)Une seule fonction, isolée, sans serveur ni base. Ex. : « decoupeAutourDuMot coupe bien le texte ».Tester une seule pièce du moteur sur un établiSuite déclarée, aucun fichier (le dossier tests/unit n'existe pas)
Fonctionnel (functional)Une vraie requête HTTP envoyée au vrai serveur, avec la vraie base. On regarde la réponse et la base.Faire rouler la voiture sur un banc d'essaiLes 36 tests sont ici (7 fichiers)
Navigateur (browser)Un vrai navigateur piloté (clics, saisie) : teste aussi le JavaScript du front.Un essai sur route avec un conducteurSuite déclarée, aucun fichier

Pourquoi le choix des tests fonctionnels ? Les risques principaux d'une messagerie sont la sécurité et les droits d'accès : qui peut lire, écrire, supprimer. Ces règles vivent côté serveur (routes, middlewares, policies, contrôleurs). Un test fonctionnel traverse toute cette chaîne en une seule requête. C'est donc le meilleur rapport effort / garantie pour ce projet.

4. Lancer les tests

Préparation (une seule fois)

  1. PostgreSQL doit tourner sur la machine (le même serveur que pour le développement).
  2. Créer une base séparée pour les tests : 
    psql -U postgres -c "CREATE DATABASE kadea_chat_test OWNER <DB_USER>;"
    Pourquoi une autre base ? Parce que les tests créent des tables, des utilisateurs, puis effacent tout à la fin. On ne veut jamais toucher aux données de développement.

Les commandes

CommandeEffet
npm testLance toutes les suites. C'est un raccourci vers node ace test (voir package.json).
node ace test functionalSeulement la suite fonctionnelle.

node ace test --tests="un non-membre ne peut pas lire la conversation (404)"Un seul test, par son titre exact.
node ace test --groups="Paramètres : changement du mot de passe"Un seul groupe.

Si un test échoue, il est marqué ✖, et Japa montre la valeur attendue et la valeur reçue, par exemple : expected 200 to equal 404 avec la ligne du fichier en cause. La commande se termine alors avec un code d'erreur (1), ce qui permet à un outil d'intégration continue de bloquer une mise en ligne.

Si PostgreSQL n'est pas démarré, rien ne se lance : on voit Acquire connection error … ECONNREFUSED. Ce n'est pas un test qui échoue : c'est la base qui n'est pas joignable (« connexion refusée »). Il suffit de démarrer le service PostgreSQL.

5. Ce qui se passe quand on tape npm test

Voici la chaîne complète. Chaque étape est détaillée dans les sections suivantes.

  1. package.json : "test": "node ace test". npm lance la commande test d'Ace (l'outil en ligne de commande d'AdonisJS).
  2. Ace lit adonisrc.ts : il exécute les hooks init (génération des fichiers #generated/controllers et #generated/policies, d'où les lignes codegen: created 4 file(s)), puis démarre bin/test.ts.
  3. bin/test.ts met NODE_ENV=test. AdonisJS charge alors .env puis .env.test, qui remplace quelques valeurs (base, session, limiteur).
  4. L'application démarre (providers, start/env.ts qui valide les variables…), mais en mode test.
  5. tests/bootstrap.ts fournit les plugins (outils) et les hooks.
  6. Hook setup global : migrations sur kadea_chat_test (création des tables), puis seeders (types de conversation, rôles, types de message).
  7. configureSuite : pour la suite functional, démarrage d'un vrai serveur HTTP local.
  8. Japa parcourt tests/functional/**/*.spec.ts. Pour chaque test : ouverture d'une transaction → le test s'exécute → annulation de la transaction.
  9. Teardown (après tous les tests) : les migrations sont annulées (tables supprimées), puis l'application s'arrête proprement.
  10. Japa affiche le bilan : combien de tests réussis, échoués.

7. adonisrc.ts : les suites de tests

Fichier : adonisrc.ts (partie tests)

tests: {
  suites: [
    {
      files: ['tests/unit/**/*.spec.ts'],
      name: 'unit',
      timeout: 2000,
    },
    {
      files: ['tests/functional/**/*.spec.ts'],
      name: 'functional',
      timeout: 30000,
    },
    {
      files: ['tests/browser/**/*.spec.ts'],
      name: 'browser',
      timeout: 300000,
    },
  ],
  forceExit: false,
},
  • suites : la liste des familles de tests (voir section 3).
  • files : où chercher les fichiers. C'est un motif glob : ** veut dire « n'importe quel sous-dossier », *.spec.ts « tout fichier qui finit par .spec.ts ». Un fichier nommé truc.ts (sans .spec) n'est jamais exécuté comme un test : c'est pour ça que helpers.ts n'est pas lancé, il est seulement importé.
  • name : le nom qu'on tape dans node ace test functional.
  • timeout : durée maximale d'un test, en millisecondes. 2 s pour un test unitaire (il doit être instantané), 30 s pour un test fonctionnel (base + serveur), 5 min pour un navigateur. Au-delà, le test est déclaré échoué : cela évite qu'un test bloqué fige tout.
  • forceExit: false : à la fin, Japa n'arrête pas brutalement Node. Il attend que tout se ferme proprement (connexion à la base, serveur), grâce au app.terminate() de bin/test.ts.

8. .env.test : un environnement à part

Fichier : .env.test

SESSION_DRIVER=memory
# Base dédiée aux tests : jamais la base de développement (créée avec CREATE DATABASE kadea_chat_test;)
DB_DATABASE=kadea_chat_test

# Limiteur en mémoire pendant les tests
LIMITER_STORE=memory

Comment ça marche : quand NODE_ENV=test, AdonisJS lit d'abord .env (toutes les variables normales : mot de passe de la base, clés Cloudinary…), puis .env.test. Les variables de .env.test écrasent celles de .env. Ici, on ne change que trois choses :

  • SESSION_DRIVER=memory : les sessions sont gardées dans la mémoire du programme, pas dans un cookie chiffré ni dans la base. C'est obligatoire pour les tests : l'outil loginAs() (voir plus bas) écrit directement la session « Alice est connectée » dans ce store mémoire. Le store memory n'est pas écrit dans config/session.ts, mais defineConfig de @adonisjs/session l'ajoute toujours automatiquement. start/env.ts accepte la valeur : SESSION_DRIVER: Env.schema.enum(['cookie', 'memory', 'database']).
  • DB_DATABASE=kadea_chat_test : la sécurité principale. Même serveur PostgreSQL, même utilisateur, mais une autre base. Les tests peuvent tout créer et tout effacer sans risque pour tes données.
  • LIMITER_STORE=memory : le limiteur d'essais (5 connexions par minute…) compte en mémoire au lieu d'écrire dans la table rate_limits. Voir config/limiter.ts : default: env.get('LIMITER_STORE', 'database').

À noter : la session et le limiteur en mémoire ne sont pas annulés par la transaction de chaque test (ils ne sont pas dans la base). Ils durent pendant tout le lancement. C'est une des raisons pour lesquelles chaque utilisateur de test reçoit une adresse e-mail unique (voir helpers.ts) : le compteur « 5 essais de connexion » est calculé par adresse IP + e-mail, donc un test ne peut pas bloquer le suivant.

9. bin/test.ts : le point de départ

Fichier : bin/test.ts (fourni par AdonisJS à la création du projet, non modifié)

process.env.NODE_ENV = 'test'

La toute première ligne. Elle dit à toute l'application « tu tournes en mode test ». Conséquences : .env.test est lu, app.inTest vaut true, le seeder des comptes de démonstration (static environment = ['development']) ne tourne pas.

  • app.booting(…) : pendant le démarrage, charger start/env.ts. C'est là que les variables (y compris celles de .env.test) sont validées. Si une variable manque, les tests ne démarrent même pas.

      ...config,

  • .testRunner() : démarre l'application en mode « lanceur de tests ».
  • await import('../tests/bootstrap.js') : charge tests/bootstrap.ts (le .js est normal : en TypeScript moderne, on écrit l'extension du fichier compilé). On sépare runnerHooks du reste (plugins, configureSuite), rangé dans config.

    2. config : les plugins et configureSuite de bootstrap.ts ;

  • .catch(…) : si le démarrage plante (base injoignable, variable manquante), on affiche l'erreur et on met le code de sortie à 1 (« échec »).

Fichier : tests/bootstrap.ts

Ce fichier répond à trois questions : quels outils les tests reçoivent (plugins), que faire avant et après tous les tests (runnerHooks), que faire pour chaque suite (configureSuite).

Shield refuse tout POST sans ce jeton (erreur 419). Les tests ne remplissent pas de formulaire : ils doivent donc demander un jeton valide. C'est aussi une preuve que la protection CSRF reste active pendant les tests : on ne l'a pas désactivée.

Les hooks avant / après tous les tests

export const runnerHooks: Required<Pick<Config, 'setup' | 'teardown'>> = {
  setup: [() => testUtils.db().migrate(), () => testUtils.db().seed()],
  teardown: [],
}
  • Le type Required<Pick<Config, 'setup' | 'teardown'>> se lit de l'intérieur : Pick prend seulement les champs setup et teardown de la config Japa ; Required les rend obligatoires. C'est ce qui permet à bin/test.ts d'écrire runnerHooks.teardown.concat(…) sans risque que teardown soit absent.
  • setup : deux fonctions exécutées une seule fois, dans l'ordre, avant le premier test.
    1. testUtils.db().migrate() lance node ace migration:run sur la base de test : toutes les tables sont créées. Cette fonction renvoie une fonction de nettoyage (migration:reset). Japa la garde et l'exécute automatiquement après le dernier test : toutes les tables sont alors supprimées.
    2. testUtils.db().seed() lance node ace db:seed : 01_reference_data_seeder.ts insère les types de conversation (Privee, groupe), les rôles (admin, membre) et les types de message (texte…). Sans ces lignes, impossible de créer une conversation ou un message. Le seeder 02_demo_users_seeder.ts ne tourne pas : il est réservé à development.
  • teardown: [] : rien à ajouter ; bin/test.ts y ajoute app.terminate().

La préparation par suite

export const configureSuite: Config['configureSuite'] = (suite) => {
  if (['browser', 'functional', 'e2e'].includes(suite.name)) {
    return suite.setup(() => testUtils.httpServer().start())
  }
}
  • Pour chaque suite, Japa appelle cette fonction.
  • Si la suite a besoin de HTTP (functional, browser, ou e2e), on démarre un vrai serveur HTTP AdonisJS avant ses tests (testUtils.httpServer().start()). Il écoute sur une adresse locale ; le client y envoie ses requêtes. Ce serveur s'arrête à la fin de la suite.
  • La suite unit n'en a pas besoin : on n'y teste que des fonctions.
  • Important : ce serveur tourne dans le même programme que les tests. C'est ce qui permet à la transaction globale de couvrir à la fois ce que fait le test et ce que fait le serveur (voir section 16).

16. La transaction globale : pourquoi les tests ne laissent aucune trace

group.each.setup(() => testUtils.db().withGlobalTransaction())

Cette ligne est en tête de presque chaque groupe. C'est le mécanisme le plus important à comprendre.

Le problème à résoudre

Chaque test crée des utilisateurs, des conversations, des messages. Sans nettoyage, après 36 tests, la base serait pleine de « Alice Test ». Pire : un test pourrait voir les données d'un autre et donner un résultat faux (par exemple, une recherche qui trouve le message d'un test précédent).

La solution : une transaction annulée

Une transaction est un ensemble de modifications de la base qui reste « en brouillon » tant qu'on ne la valide pas (commit). On peut tout annuler d'un coup (rollback), comme si rien n'avait eu lieu.

  1. Avant le test : withGlobalTransaction() ouvre une transaction globale : toutes les requêtes Lucid de l'application passent désormais par elle.
  2. Pendant le test : le test crée Alice et Bob, envoie des requêtes ; le serveur (qui tourne dans le même programme) enregistre des messages… Tout passe par la même transaction. À l'intérieur, tout est visible et cohérent.
  3. Après le test : withGlobalTransaction() a renvoyé une fonction rollbackGlobalTransaction. Japa l'appelle : tout est annulé. La base redevient identique à ce qu'elle était après les seeders.

C'est aussi très rapide : annuler une transaction coûte presque rien, beaucoup moins que vider toutes les tables.

Ce qu'elle n'annule pas

  • Ce qui n'est pas dans PostgreSQL : sessions et compteurs du limiteur (en mémoire), e-mails simulés.
  • Les envois vers des services externes (Cloudinary, Brevo). Aucun test n'en fait : les e-mails sont simulés avec mail.fake(), et aucun test n'envoie de fichier.

Les trois niveaux de nettoyage, du plus fin au plus large :

1. Après chaque test : rollback de la transaction (données du test).
2. Après tous les tests : migration:reset (toutes les tables).
3. À la toute fin : app.terminate() (connexions fermées).

Remarque technique : dans la version installée de Lucid, withGlobalTransaction() est marquée « dépréciée » (ancienne) au profit de wrapInGlobalTransaction(), qui fait exactement la même chose. Elle fonctionne ; on pourrait simplement la renommer un jour.

24. « les pages envoient une CSP et le script en ligne porte son nonce »

Suivons le test 5 « on ne peut pas supprimer le message d'un autre (403) » à travers tout le système.

  1. Avant le test : group.each.setup ouvre la transaction globale.
  2. Préparer : creeUtilisateur × 2 insère Alice et Bob (mots de passe hachés par withAuthFinder). chercheOuCreeConversationPrivee crée la conversation de type Privee (ligne venue du seeder) et deux lignes dans user_conversations.

  4. Le serveur de test reçoit la requête : middlewares (session lue → Shield vérifie le CSRF → auth reconnaît Alice → Bouncer initialisé) → route → contrôleur → message enregistré → 201.
  5. Message.query()…firstOrFail() relit le message en base (toujours dans la transaction).

20. Questions possibles du jury, et réponses

Quel outil de test as-tu utilisé, et pourquoi ?
Japa, le lanceur officiel d'AdonisJS. Il est déjà intégré au framework (node ace test, bin/test.ts), avec des plugins pour la session, la connexion (loginAs), le CSRF et la base. Pas besoin d'installer et de configurer Jest ou Vitest.
Quel type de tests ?
Des tests fonctionnels : de vraies requêtes HTTP vers le vrai serveur avec une vraie base PostgreSQL. Ils traversent toute la chaîne (middlewares, policies, contrôleurs, vues, base). C'est le plus utile pour une messagerie, où le risque principal est l'accès aux données des autres.
Tes tests ne risquent-ils pas d'abîmer tes données ?
Non. .env.test les dirige vers une base séparée, kadea_chat_test. Et chaque test tourne dans une transaction annulée à la fin, donc même la base de test reste propre.
Comment un test « se connecte-t-il » ?
Avec .loginAs(user) du plugin Auth : il écrit une session « connecté » dans le store mémoire (d'où SESSION_DRIVER=memory dans .env.test). Le vrai formulaire de connexion est testé à part (test 26), ainsi que sa limite d'essais (test 27).
Et le CSRF, tu l'as désactivé pour les tests ?
Non. Les tests demandent un jeton valide avec .withCsrfToken(). Sans lui, Shield répondrait 419 : la protection reste donc réellement active et vérifiée.
Pourquoi 404 et pas 403 quand un intrus ouvre une conversation ?
Pour ne pas révéler qu'elle existe. Un 403 confirmerait l'existence de la conversation n°7 ; un 404 ne dit rien. Le 403 est utilisé quand la personne voit déjà la ressource mais n'a pas le droit d'agir (supprimer le message d'un autre, gérer un groupe sans être admin).
Quel est ton test préféré / le plus important ?
« Au-delà de 5 essais, la requête est refusée, même avec le bon mot de passe » : il prouve que le limiteur agit avant la vérification, donc qu'une attaque par force brute est bloquée. Ou « l'administrateur retire un membre, qui perd aussitôt l'accès » : il vérifie une suite d'actions complète.
Qu'est-ce que tu n'as pas testé ?
L'envoi de fichiers (Cloudinary, service externe), le JavaScript du navigateur et le parcours d'inscription complet. Les suites unit et browser sont prêtes dans adonisrc.ts pour les ajouter. Prochaine étape : lancer les tests automatiquement à chaque push avec GitHub Actions.
Combien de tests ?
36 tests, dans 12 groupes et 7 fichiers, tous dans la suite functional.
Qu'est-ce qu'une assertion ?
Une vérification : « j'affirme que le code de réponse vaut 404 ». Si c'est faux, le test s'arrête et échoue en montrant la valeur attendue et la valeur reçue.
