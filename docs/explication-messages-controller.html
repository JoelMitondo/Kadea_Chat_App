messages_controller.ts expliqué ligne par ligne

Kadea Chat · envoi, modification et suppression des messages · fichier : app/controllers/messages_controller.ts

Ce contrôleur gère la vie d'un message : l'envoyer (en privé ou dans un groupe, avec ou sans fichier), le modifier et le supprimer. Après chaque action, il répond à l'auteur et prévient les autres participants en temps réel.

Le parcours d'un message, résumé par le commentaire en tête du fichier : formulaire → route → ce contrôleur (validation, droits, base de données) → réponse à l'expéditeur + événement temps réel vers les autres participants.

Une seule méthode fait le vrai travail d'envoi : envoieMessage. Les méthodes privée et groupe vérifient seulement que tu es membre, puis lui passent la main.

Le serveur fabrique le HTML de la bulle : le navigateur reçoit une bulle déjà prête et n'a qu'à l'insérer.

Les droits sont dans une policy : « seul l'auteur peut modifier ou supprimer » et « on ne peut pas écrire à quelqu'un qui nous a bloqué » sont rangés dans app/policies/conversation_policy.ts. Le contrôleur demande seulement à Bouncer.

La policy Bouncer : app/policies/conversation_policy.ts

Bouncer est le système d'autorisation d'AdonisJS. Une policy est une classe qui rassemble les règles « qui a le droit de faire quoi » sur une ressource. Avant, chaque règle était un if écrit dans le contrôleur. Maintenant, elle a un nom et une place à part.

export default class ConversationPolicy extends BasePolicy {
  modifierMessage(user: User, message: Message) {
    if (message.userId !== user.id) {
      return AuthorizationResponse.deny('Vous ne pouvez modifier que vos propres messages.')
    }
    return true
  }

  supprimerMessage(user: User, message: Message) {
    if (message.userId !== user.id) {
      return AuthorizationResponse.deny('Vous ne pouvez supprimer que vos propres messages.')
    }
    return true
  }

  async ecrireA(user: User, otherUserId: User['id']) {
    if (await aBloque(otherUserId, user.id)) {
      return AuthorizationResponse.deny("Impossible d'envoyer ce message à cet utilisateur.")
    }
    return true
  }
}
  • Chaque méthode est une règle. Le premier paramètre est toujours l'utilisateur connecté, que Bouncer fournit tout seul. Les suivants sont ce qu'on lui passe.
  • return true : autorisé.
  • AuthorizationResponse.deny('...') : refusé, avec un message en français.
  • ecrireA est async : elle interroge la base (aBloque). Une règle peut donc faire des requêtes.

Côté contrôleur, une seule ligne :

await bouncer.with(ConversationPolicy).authorize('modifierMessage', message)
  • bouncer est dans le contexte (HttpContext), grâce au middleware app/middleware/initialize_bouncer_middleware.ts.
  • .with(ConversationPolicy) choisit la policy, et .authorize('modifierMessage', message) appelle la règle.
  • Si la règle refuse, authorize lance une erreur E_AUTHORIZATION_FAILURE. La suite du contrôleur n'est pas exécutée : pas besoin de if ni de return.
  • Cette erreur arrive dans app/exceptions/handler.ts, qui reprend le message de la policy et met le code 403. Le JavaScript reçoit donc toujours { message: '...' } en 403, comme avant.

Pourquoi 404 pour l'appartenance, mais 403 dans la policy ? chercheParticipationPrivee / Groupe restent dans le contrôleur et renvoient une 404 : on ne révèle pas à un non-membre qu'une conversation existe. La policy décide ensuite de ce qu'un membre a le droit de faire, et un refus est alors une 403.

2. enregistreMessagePrive et enregistreMessageGroupe

async enregistreMessagePrive(ctx: HttpContext) {
  const user = ctx.auth.getUserOrFail()
  const membership = await chercheParticipationPrivee(
    user.id,
    Number(ctx.params.id)
  ).firstOrFail()
  return this.envoieMessage(ctx, membership, 'private')
}
  • ctx entier : la méthode garde le contexte complet, car elle doit le transmettre à envoieMessage.
  • chercheParticipationPrivee(...).firstOrFail() : (de chat_service.ts) cherche ta ligne dans user_conversations pour cette conversation privée. Si tu n'en fais pas partie, erreur 404 : impossible d'écrire dans la conversation des autres en changeant l'adresse.
  • this.envoieMessage(ctx, membership, 'private') : passe la main à la méthode commune, en précisant qu'il s'agit d'une conversation privée.
async enregistreMessageGroupe(ctx: HttpContext) {
  const user = ctx.auth.getUserOrFail()
  const membership = await chercheParticipationGroupe(user.id, Number(ctx.params.id))
    .preload('conversation') // pour connaître le nom du groupe
    .firstOrFail()
  return this.envoieMessage(ctx, membership, 'group')
}

Même principe pour un groupe, avec chercheParticipationGroupe (identique mais filtre le type 'Publique'). Le preload('conversation') charge le groupe pour connaître son titre, affiché dans la notification des autres membres.

3. modifieMessage : modifier son message

async modifieMessage({ auth, bouncer, params, request, response, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const { content } = await request.validateUsing(updateMessageValidator)
  const message = await Message.findOrFail(params.id)
  • validateUsing : vérifie le nouveau texte (obligatoire, 2000 caractères max). En cas d'erreur, la méthode s'arrête ici.
  • Message.findOrFail(params.id) : cherche le message par son identifiant, ou renvoie une 404 s'il n'existe pas.
  // Règle d'autorisation : app/policies/conversation_policy.ts (403 si ce n'est pas l'auteur)
  await bouncer.with(ConversationPolicy).authorize('modifierMessage', message)
  if (message.isDeleted) {
    return response.badRequest({ message: 'Ce message a été supprimé.' })
  }
  • Vérification des droits : seul l'auteur peut modifier. Sinon, la règle modifierMessage de la policy refuse, et la réponse est un 403. C'est la vraie protection : le bouton « Modifier » caché dans la page ne suffit pas, car on peut envoyer la requête à la main.
  • Message supprimé : on ne modifie pas un message supprimé. Code 400 (badRequest).
  message.content = content
  await message.save()

Remplace le texte et enregistre. Lucid met aussi à jour updatedAt, et c'est grâce à ça que construitVueMessage affichera « modifié » (updatedAt plus tard que createdAt).

  await message.load('statuses', (statusQuery) => {
    statusQuery.whereNot('userId', user.id)
  })

load charge une relation sur un modèle déjà récupéré (là où preload s'utilise pendant la requête). On charge les statuts des autres personnes, pour que la bulle renvoyée garde les bonnes coches (lu / envoyé).

  const data = await this.construitReponseMessage(message, user.id, view)
  await this.previensAutresParticipants(message, user, data.isLast)
  return response.ok(data)
}
  1. construitReponseMessage : fabrique la nouvelle bulle en HTML et les infos de la liste (point 7).
  2. previensAutresParticipants : envoie la modification en temps réel aux autres (point 6). data.isLast leur dit si c'était le dernier message, donc si l'aperçu de la liste doit changer.
  3. response.ok(data) : code 200 avec le JSON, que le JavaScript de la page utilise pour remplacer la bulle.

4. supprimeMessage : supprimer son message

async supprimeMessage({ auth, bouncer, params, response, view }: HttpContext) {
  const user = auth.getUserOrFail()
  const message = await Message.findOrFail(params.id)

  await bouncer.with(ConversationPolicy).authorize('supprimerMessage', message)

Même début que la modification : le message doit exister (sinon 404) et t'appartenir (sinon la règle supprimerMessage refuse, donc 403).

  message.merge({ isDeleted: true, deletedAt: DateTime.now(), content: null })
  await message.save()

Suppression « douce » (soft delete) : la ligne reste en base, marquée comme supprimée avec la date. C'est pourquoi les autres voient « Ce message a été supprimé » à sa place, au lieu d'un trou dans la discussion. merge copie les valeurs dans l'objet, et save les enregistre.

Nouveau : content: null. Le texte est aussi effacé de la base. Avant, il restait stocké, simplement caché à l'affichage : quelqu'un ayant accès à la base pouvait encore le lire. Maintenant, rien du contenu supprimé n'est conservé. Seule la place du message reste, pour garder l'ordre de la discussion.

  const attachments = await MessageAttachment.query().where('messageId', message.id)
  for (const file of attachments) {
    await supprimeFichierParLien(file.filePath)
  }
  await MessageAttachment.query().where('messageId', message.id).delete()

Le fichier joint, lui, est vraiment supprimé :

  1. On récupère les fichiers joints du message.
  2. Pour chacun, supprimeFichierParLien (de cloudinary_service.ts) le supprime de Cloudinary. Elle utilise extraitIdentifiantCloudinary pour retrouver le publicId et le type à partir du lien, puis appelle cloudinary.uploader.destroy(...) avec invalidate: true (vide aussi le cache). Elle ne lance jamais d'erreur : en cas d'échec, elle l'écrit dans les logs et renvoie false.
  3. On supprime ensuite les lignes de message_attachments en base, en une seule requête DELETE.
  const data = await this.construitReponseMessage(message, user.id, view)
  await this.previensAutresParticipants(message, user, data.isLast)
  return response.ok(data)
}

Même fin que la modification : la bulle « Ce message a été supprimé » est renvoyée à l'auteur et envoyée en temps réel aux autres.

5. envoieMessage : l'envoi en 6 étapes

private async envoieMessage(
  ctx: HttpContext,
  membership: UserConversation,
  kind: ConversationKind
) {
  const { auth, bouncer, request, response, view, logger } = ctx
  const user = auth.getUserOrFail()
  const { content, attachment } = await request.validateUsing(sendMessageValidator)
  const conversationId = membership.conversationId
  • membership : ta participation, déjà vérifiée par la méthode appelante.
  • kind : 'private' ou 'group'.
  • validateUsing(sendMessageValidator) : vérifie le texte et le fichier. Si le fichier est trop gros ou d'une extension refusée, la requête s'arrête avec une erreur 422.
  • conversationId : pris dans la participation vérifiée, pas directement dans l'adresse.

Étape 1 : au moins un texte ou un fichier

if (!content && !attachment) {
  return response.unprocessableEntity({
    errors: [{ field: 'content', message: 'Écrivez un message ou joignez un fichier.' }],
  })
}

Les deux sont facultatifs dans le validateur, mais il en faut au moins un. Code 422, avec le champ concerné pour que la page affiche l'erreur au bon endroit.

Étape 2 : les destinataires et le blocage

const otherMemberships = await UserConversation.query()
  .where('conversationId', conversationId)
  .whereNot('userId', user.id)

Tous les autres participants : une personne en privé, plusieurs dans un groupe. Cette liste servira trois fois : le blocage, les statuts « non lu » et le temps réel.

if (kind === 'private' && otherMemberships.length > 0) {
  await bouncer.with(ConversationPolicy).authorize('ecrireA', otherMemberships[0].userId)
}

La règle ecrireA de la policy appelle aBloque(bloqueur, bloqué) (de block_service.ts), qui cherche une ligne dans blocked_users et renvoie true si elle existe. Attention à l'ordre : on demande si l'autre t'a bloqué. Dans ce cas, la règle refuse et la réponse est un 403. Le message d'erreur reste vague volontairement : il ne dit pas « cette personne vous a bloqué ». Le blocage ne s'applique qu'aux conversations privées.

// Qui est en ligne en ce moment ? Pour eux, le message arrive tout de suite (statut « reçu »).
// Les autres le recevront à leur prochaine connexion (voir marqueMessagesCommeRecus).
const onlineRecipients = await User.query()
  .whereIn('id', otherMemberships.map((other) => other.userId))
  .where('isOnline', true)
  .select('id')
const onlineIds = new Set(onlineRecipients.map((recipient) => recipient.id))

Nouveau : qui est en ligne ? C'est la base du statut « reçu » (deux coches grises).

  • Parmi les destinataires, on garde ceux dont isOnline est vrai. Cette colonne est tenue à jour par start/transmit.ts quand une page s'ouvre ou se ferme.
  • new Set(...) : un ensemble d'identifiants. onlineIds.has(id) répond très vite à « est-il en ligne ? », sans parcourir un tableau à chaque fois.
  • Ceux qui sont en ligne recevront le message tout de suite, en temps réel. Leur statut peut donc être créé directement à « reçu » (voir l'étape 5).

Étape 3 : envoyer le fichier vers Cloudinary

let messageTypeName = 'texte'
let fileUrl: string | null = null

Valeurs par défaut pour un message texte. L'extension est mise en minuscules, pour que PHOTO.JPG soit reconnu comme jpg. Sans fichier, elle vaut ''.

  • Image ou document : décidé selon l'extension.
  • envoieImage / envoieDocument : (de cloudinary_service.ts) envoient le fichier depuis son chemin temporaire (tmpPath) vers kadea-chat/messages/<uuid> et renvoient son lien HTTPS. L'image est envoyée en type image, le document en type raw avec son extension dans le nom.

const messageType = await donneTypeMessage(messageTypeName)

donneTypeMessage vient de chat_service.ts :

Étape 4 : le message précédent

const previousMessage = await donneDernierMessage(conversationId)

donneDernierMessage vient de chat_service.ts. Cette requête était écrite plusieurs fois dans le code, elle est maintenant au même endroit :

export function donneDernierMessage(
  conversationId: number,
  options: { withAuthor?: boolean; client?: TransactionClientContract } = {}
) {
  const query = Message.query({ client: options.client })
    .where('conversationId', conversationId)
    .orderBy('id', 'desc')
  if (options.withAuthor) {
    query.preload('user')
  }
  return query.first()
}
  • Tri par id décroissant : le plus grand identifiant est le plus récent.
  • withAuthor (facultatif) : charge l'auteur, pour l'aperçu « Jo : ... » d'un groupe.
  • client (facultatif) : pour lire à l'intérieur d'une transaction.
  • = {} : si on ne passe rien, les options sont vides.

Le dernier message avant celui qu'on va créer (ou null). Il sert à décider si un séparateur de jour (« Aujourd'hui ») doit être affiché avant la nouvelle bulle. Il faut le lire avant la création, sinon on trouverait le nouveau message lui-même.

Étape 5 : l'enregistrement dans une transaction

Si une seule écriture échoue, la base annule toutes les autres. trx représente cette transaction, et chaque écriture la reçoit avec { client: trx }. Sans ça, on pourrait se retrouver avec un message sans statuts, invisible dans les compteurs.

  • filePath : le lien Cloudinary.
  • mimeType : reconstruit à partir de type et subtype, par exemple image/png. Valeur par défaut : application/octet-stream (« fichier binaire quelconque »).
  • fileSize : la taille en octets.

La colonne status suit le trajet du message :

Comme c'est un update direct, on écrit le nom de colonne SQL (last_message_id). Le return fait de newMessage le résultat de la transaction.

Étape 6 : répondre et prévenir

await message.load('attachments')
await message.load('statuses')

Charge le fichier joint et les statuts du nouveau message. construitVueMessage a besoin des deux pour dessiner la bulle : le fichier, et les coches. Si tous les destinataires étaient en ligne, la bulle s'affiche chez toi directement avec deux coches grises, grâce à isDelivered.

besoinSeparateurDeJour (de chat_service.ts) renvoie true si :

  • ou les deux messages ne sont pas du même jour (clé aaaa-mm-jj différente, à l'heure de Kinshasa).

Ensuite, construitReponseMessage prépare la réponse (point 7).

  recipients: otherMemberships,
})

load('user') charge l'auteur, pour afficher son nom dans un groupe. Puis previensNouveauMessage (de realtime_service.ts) prévient chaque destinataire en temps réel :

  • pour chaque destinataire, il fabrique côté serveur le HTML de la bulle vue par lui (message reçu, nom de l'auteur dans un groupe), avec partials/message-item ;
  • il l'envoie sur le canal personnel de ce destinataire (users/<id>), avec Transmit ;
  • dans son navigateur, realtime.js reçoit l'événement et message.js insère la bulle et met à jour la liste ;
  • chaque destinataire a son propre try/catch : si l'un échoue, les autres sont quand même prévenus, et un problème de temps réel ne fait jamais échouer l'envoi.

conversationName vaut le titre du groupe, ou null en privé. Le ?. évite une erreur si la conversation n'a pas été chargée.

return response.created(data)

Code 201 (Created) : une ressource a été créée. Le JSON contient la bulle à insérer chez l'auteur.

6. previensAutresParticipants : après modification ou suppression

private async previensAutresParticipants(message: Message, sender: User, isLast: boolean) {
  const conversation = await Conversation.query()
    .where('id', message.conversationId)
    .preload('type')
    .firstOrFail()
  const kind: ConversationKind = conversation.type.type === GROUP_TYPE ? 'group' : 'private'

Contrairement à l'envoi, la modification et la suppression partent de l'adresse /messages/:id, qui ne dit pas s'il s'agit d'un groupe. On charge donc la conversation et son type. conversation.type.type : la relation type, puis sa colonne type ('Privee' ou 'Publique'). GROUP_TYPE vaut 'Publique'.

  const recipients = await UserConversation.query()
    .where('conversationId', message.conversationId)
    .whereNot('userId', sender.id)

  await message.load('user') // pour le nom de l'auteur dans un groupe

  await previensMessageModifie({ message, kind, isLast, recipients })
}

On récupère les autres participants, on charge l'auteur, puis previensMessageModifie (de realtime_service.ts) leur envoie la nouvelle version de la bulle sur leur canal personnel. isLast leur indique s'il faut aussi mettre à jour l'aperçu dans la liste.

Le parcours complet d'un envoi

Tu écris "Salut" et tu appuies sur Envoyer
  → message.js : fetch POST /conversations/12/messages
  → enregistreMessagePrive
      → chercheParticipationPrivee + firstOrFail     (tu en fais partie ? sinon 404)
  → envoieMessage
      1. texte ou fichier ?                          (sinon 422)
      2. autres participants + policy ecrireA       (bloqué ? 403)
         + qui est en ligne ? (onlineIds)
      3. fichier → Cloudinary                        (échec ? 422)
      4. message précédent
      5. transaction : message + fichier + statuts (sent ou delivered) + dernier message
         (échec ? annulation + suppression du fichier sur Cloudinary)
      6. bulle HTML (construitReponseMessage)
         + temps réel vers les autres (previensNouveauMessage)
  → 201 Created : message.js insère la bulle chez toi

Ce qui a été remarqué

Corrigé depuis la première version de ce document :

• Identifiants non numériques : les routes portent maintenant .where('id', ID_NUMERIQUE). /conversations/abc/messages ou /messages/abc donnent une 404, et plus une erreur 500.

• Le commentaire en double au-dessus de envoieMessage a été retiré.

• Le texte d'un message supprimé n'est plus conservé en base (content: null).

• Les droits sont regroupés dans une policy au lieu d'être des if répétés.

Toujours d'actualité, la suppression sans transaction : dans supprimeMessage, le message est marqué supprimé, puis le fichier est effacé de Cloudinary, puis de la base. Si la suppression Cloudinary échoue, supprimeFichierParLien renvoie false sans erreur, mais la ligne en base est quand même supprimée. Le fichier peut donc rester sur Cloudinary sans plus être référencé.

Un message déjà supprimé peut être « resupprimé » : supprimeMessage ne vérifie toujours pas isDeleted, contrairement à modifieMessage. Ce n'est pas grave, mais deletedAt est alors remplacé par une nouvelle date.

« En ligne » ne veut pas dire « page ouverte » : isOnline repose sur la connexion temps réel. Si elle vient de tomber sans que les 8 secondes de délai soient passées, un message peut être marqué « reçu » alors qu'il n'est pas encore arrivé. C'est un cas rare, et il se corrige à la reconnexion.
